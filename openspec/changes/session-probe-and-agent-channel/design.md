# Design

## Context

See proposal.md for the motivation and specs/ for the required behavior.

Current state that shapes the approach:
- The service runs as LocalSystem in session 0. It lists the processes of the child's sessions itself (`ProcessControl.ListProcesses`: pid, session, exe path, start time, thread state) and suspends and resumes them itself. `ListProcesses` leaves out a process whose start time it cannot read (`OpenProcess` fails).
- The Session Agent (`ParentalControl.Agent.exe`) runs as the child. `SessionTracker.EnsureAgentRunning` starts it with `WTSQueryUserToken` + `CreateProcessAsUserW` (`SessionManager.LaunchProcessInSession`) and closes the handles of `PROCESS_INFORMATION` at once. The installer also starts it at each sign-in through the value `ParentalControlAgent` below `HKLM\...\CurrentVersion\Run`.
- The agent talks to the service over HTTP on `127.0.0.1:5050`, with no authentication: `GET /api/agent/status?user=` every 5 s, `POST /api/agent/activity` every 20 s (the Foreground Window sample, the only source of Category Usage and of `ForegroundHistory`), `POST /api/agent/prompt/respond`, `POST /api/agent/capture` (user in the header `X-User`) and `POST /api/agent/session-ending` (session ID in the body).
- The agent keeps one instance per user with the named mutex `Global\ParentalControlAgent_{UserName}`. `EnsureAgentRunning` finds an agent by its image path in the session.
- The default App Rules put the install folder in System (`CategoryDefaults`), so the window of the Session Agent counts no time. `SuspensionPlanner` never suspends the agent exe, an exe with the file name `msedgewebview2.exe`, or an exe below the Windows folder.
- `build.ps1` publishes the service, the admin app and the agent self-contained for `win-x64`. All projects target `net8.0`. .NET 8 support ended on 2026-11-10; .NET 10 (LTS) has support until 2028-11-14.
- Existing holes that this change also closes: any process can poll `/api/agent/status?user=Kid`, which clears the capture request of the parent and shows the active prompt of any user. `/api/agent/prompt/respond` accepts any prompt ID.

Threat model: the child is 10 years old and has a standard account. It can run any program in its session, kill or replace its agent process, read and write the memory of the agent (same user, same integrity level), set its own user environment variables, change the DACL of its own processes and threads (it is their owner), create desktops with its own security descriptor, read the CPU times of each process (`NtQuerySystemInformation` gives them to each user), and send any request to `127.0.0.1:5050`. It cannot run code as SYSTEM or as an administrator.

### What a SYSTEM service in session 0 can see
- **Can see:** each process in each session, its user, its session, its exe path, its start time and the state of its threads (`OpenProcess`, `QueryFullProcessImageNameW`, `GetProcessTimes`, `ProcessIdToSessionId`, `NtQuerySystemInformation`). The lock state of a session (WTS notifications).
- **Cannot see:** the Foreground Window of another session. `GetForegroundWindow`, `GetGUIThreadInfo` and `GetWindowThreadProcessId` work only on the desktop of the calling thread. A thread in session 0 cannot attach to the window station `WinSta0` of session 1, because `OpenWindowStationW` and `OpenDesktopW` resolve names in the session of the caller. The WTS functions give the state of a session, not its windows. We found no documented API that gives the Foreground Window of another session to a process in session 0.
- So the facts about the Foreground Window must come from a process in the session of the child. That process must not run as the child.

## Goals / Non-Goals

**Goals:**
- No limit depends on data that a process of the child can write.
- A child action that hides the Foreground Window from the service fails closed (a lock), not open (free time).
- The child cannot stop the start of the Session Agent (#32).
- Each agent message has the user and the session of the agent that the service started.
- The pure logic (sample counting, blind-sample budget, probe outage, channel framing, launch record) runs and is tested on the Mac.

**Non-Goals:**
- Trustworthy data from the Session Agent. The child controls that process. This design does not try to protect it, and it does not need to.
- Protection against an administrator or against code that runs as SYSTEM.

### D1. The service gets the Foreground Window from a Session Probe that runs as SYSTEM
*Decided by the orchestrator under the user's delegation (2026-11-26).*

The service starts `ParentalControl.Probe.exe` in each session of a Restricted User, with a SYSTEM token that it moves to that session. The probe has no window. At random intervals with a mean of about 5 seconds (D4) it reads the windows of the input desktop that the child can use (the Foreground Window, the focus, the visible child windows of other processes, the window under the cursor) and sends a sample to the service. Category Usage, `ForegroundHistory`, App Usage and the live activity of the admin page take only these samples and the process list of the service.

Why SYSTEM: a process of the child cannot open a SYSTEM process for `PROCESS_TERMINATE`, `PROCESS_SUSPEND_RESUME`, `PROCESS_VM_READ` or `PROCESS_VM_WRITE`. The explicit security descriptor of the probe process and thread (D2) gives the child no access, and the mandatory label (System integrity) blocks write access from the medium integrity level. UIPI blocks window hooks and window messages from the child into a process at a higher integrity level, and the probe has no window anyway.

Rejected alternatives:
- **A helper that runs as the child.** It has the same weak point as the agent: the child can kill it, inject code into it, or replace its data.
- **Agent samples checked against the process list.** The service can check that the reported pid exists in the session with that exe path. But the child can report a Study exe that runs in the background while a game is in front. The check does not find this.
- **Count from the process list only** (a category counts while one of its processes runs). `add-app-categories` D1 rejected it: launchers and tray helpers count all day. The parent chose Foreground Window counting.
- **Audio, GPU or input heuristics** to detect use. They are a separate topic (idle detection, background video) and are out of scope.

### D2. How the service starts the Session Probe
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for S3, S4, N5–N8, N10, for S13, N12, N17, N21, for S15, for S20, N26, for the spike results of tasks 1.4 and 1.5, and for the review decisions on the end classification).*

The service (`SessionProbeHost`, new) starts the probe for each session of a Restricted User at once at `WTS_SESSION_LOGON` and `WTS_SESSION_UNLOCK` (N10), after the restart delay that follows each end that the service did not ask for (S15 and spike 1.4, see "Watchdog and restart" and "The end of a probe at a sign-out" below), and in the 60-second tick if no probe of the service runs in that session. It never starts a probe in a session that got `WTS_SESSION_LOGOFF` or that is gone.

WinAPI calls, in order:
1. `OpenProcessToken(GetCurrentProcess(), TOKEN_DUPLICATE | TOKEN_QUERY | TOKEN_ASSIGN_PRIMARY | TOKEN_ADJUST_DEFAULT | TOKEN_ADJUST_SESSIONID)`.
2. `CreateRestrictedToken(..., DISABLE_MAX_PRIVILEGE, ...)`: the probe keeps only `SeChangeNotifyPrivilege`. It needs no privilege, because it opens no process (D3). The spike (task 1.3) also tries `WRITE_RESTRICTED` with the restricting SID `S-1-5-18` (N7). The probe uses it only if the probe still samples and writes its pipe with it.
3. `DuplicateTokenEx(..., TokenPrimary)`, `SetTokenInformation(TokenSessionId, sessionId)` (needs `SeTcbPrivilege` in the service, which LocalSystem has), and `SetTokenInformation(TokenDefaultDacl)` with a DACL for SYSTEM only. So each object that the probe or its runtime creates is closed to the child.
4. The environment block: `CreateEnvironmentBlock(out env, systemToken, false)` (the environment of SYSTEM, never that of the child). The service removes each variable that starts with `DOTNET_`, `COMPlus_` or `CORECLR_`, and then adds `DOTNET_EnableDiagnostics=0` (no diagnostic IPC pipe, no debugger, no profiler) and `DOTNET_DISABLE_GUI_ERRORS=1` (S4, S3). The child can set `DOTNET_STARTUP_HOOKS`, `DOTNET_ROOT`, `COMPlus_*` and `PATH` in `HKCU\Environment`; none of them reaches the probe.
5. The pipe (D3), with an explicit SYSTEM-only security descriptor (N1). The service creates both ends non-inheritable. Directly before step 7 it makes an inheritable duplicate of the write end, and closes that duplicate directly after step 7. Steps 5 to 7 hold the process-wide lock `ProcessLaunchLock` (Core), which `UpdateService` also takes for its `Process.Start`. So no other process start of the service can inherit the handle (N6).
6. `InitializeProcThreadAttributeList` and `UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_HANDLE_LIST)` with only the inheritable duplicate.
7. `CreateProcessAsUserW(token, lpProcessAttributes and lpThreadAttributes with a DACL for SYSTEM only (S4), bInheritHandles: true, EXTENDED_STARTUPINFO_PRESENT | DETACHED_PROCESS | CREATE_UNICODE_ENVIRONMENT | HIGH_PRIORITY_CLASS, env, "{app}\probe", STARTUPINFOEX with lpDesktop "winsta0\default")`.
8. The service keeps the process handle. `WaitForSingleObject` on it (through `RegisteredWaitHandle`) tells the service that the probe ended.

**No Job Object (N17).** The first revisions put the probe into a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The remarks of `AssignProcessToJobObject` say that all processes of a job must run in the same session, and the job of the service is in session 0. So that step always fails for the probe. The design drops it, and with it `CREATE_SUSPENDED` and `ResumeThread`. The pipe and the leftover cleanup below end a probe.

**`DETACHED_PROCESS`, not `CREATE_NO_WINDOW` (S13).** With `CREATE_NO_WINDOW`, the new console process gets no visible console window, but the console allocation design of Windows Terminal (spec #7335) says that a console host (`conhost.exe`) still starts for it with an invisible window. That is an extra SYSTEM process with a window in the session of the child. With `DETACHED_PROCESS`, a console process gets no console and no console host. The probe needs no console. The spec is a design document, not a guarantee, so task 1.3 proves it on the VM: the probe has no `conhost.exe` child, and no window belongs to the probe or to such a child.

**Priority (N8, N12).** A standard user can raise its own processes to High, but not to Realtime. The probe runs at `HIGH_PRIORITY_CLASS`, and its sampler thread at `THREAD_PRIORITY_TIME_CRITICAL` (base priority 15). A thread of the child can reach 15 too (High class and time-critical), but not more. So a CPU load of the child shares the CPU with the sampler in turns and cannot stop it. The probe uses a few milliseconds per sample. Task 1.5 measures the gaps under a load of time-critical threads of `Kid`. The service sample time comes from the probe (D3), so a delay of the service reader does not change the counted time (S9).

**The spike disproved the turn (task 1.5).** On VM 102, 12 time-critical threads of `Kid` in a High process on 8 vCPUs gave sample gaps of up to 34.2 seconds, and single calls stalled (one sample took 24.2 seconds, one `WindowFromPoint` call 2.9 seconds). The cause is not confirmed. It can be a starvation of the vCPUs on the Proxmox host, or a lock in win32k that a starved thread of lower priority holds. *Decided by the orchestrator under the user's delegation (2026-11-27):* the design does not raise the priority. `REALTIME_PRIORITY_CLASS` stays rejected (N12), and it does not help if the cause is a lock in win32k. The gap rule of D5 handles the gap itself, whatever its cause. Task 9.1 repeats the measurement on the child's PC.

The probe program (S3, S4):
- It targets `net10.0-windows` and `build.ps1` publishes it self-contained for `win-x64` into `{app}\probe`, like the other parts. So no runtime search happens, and no `DOTNET_ROOT` applies. Only administrators can change `{app}\probe`. The move of all projects from .NET 8 to .NET 10 is a separate chore that comes before group 3 (task 1.0): .NET 8 is out of support, and one runtime for all parts is simpler than a mixed solution. It changes CI (`setup-dotnet`), the snapshot `test-base` of the VM, and `CLAUDE.md`.
- It is a console program (`OutputType` `Exe`), not `WinExe`. With `DETACHED_PROCESS` it gets no console and no console host (S13). A `WinExe` apphost shows a message box when the start fails; a console apphost writes to `stderr`, which goes nowhere.
- The project sets `<StartupHookSupport>false</StartupHookSupport>` (N21). The runtime then ignores `DOTNET_STARTUP_HOOKS`, also if the environment strip of step 4 has a bug.
- At the start of `Main`: `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)` and `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)`. The assembly has `DefaultDllImportSearchPaths(System32)`. `WerSetFlags` has no documented flag that turns off the error UI, so the design does not rely on it; task 1.6 proves that a forced crash shows no window.
- It references no project of the solution: no Core (no Serilog, no database code, no HTTP code), no Domain. It has its own small set of P/Invoke declarations. It uses no COM, no `Microsoft.Win32.SystemEvents` (it creates a hidden window), no `System.Windows.Forms` and no WPF. Its sampler thread is an MTA thread at `THREAD_PRIORITY_TIME_CRITICAL` and creates no window and no hook (S8: `SetThreadDesktop` fails else). It writes no file: its few log lines go through the pipe (D3).

How a probe ends:
- The primary mechanism is the pipe. When the service process ends, also after a crash, the read end closes, the next write of the probe fails with `ERROR_BROKEN_PIPE` or `ERROR_NO_DATA`, and the probe exits within one sample interval (at most 10 seconds).
- The service ends a probe with `TerminateProcess` at the sign-out of its session (`WTS_SESSION_LOGOFF`) and at the service stop.
- At its start, the service ends each leftover probe of an earlier run: a process whose exe path is `{app}\probe\ParentalControl.Probe.exe` and whose token user is `S-1-5-18` (N5). It reads the token user with `OpenProcessToken` + `GetTokenInformation(TokenUser)`. A process with that path and another user is not ended; the service logs it.
- The hard rule covers the programs of the child, not this helper of the service.

**Watchdog and restart (S15).** Re-review 3 showed that a probe that hangs never ends, so the old restart rule (only after the end) never acts, and that a probe that crashes waits up to 60 seconds for the tick. The probe parses window data that the child controls, so a crash or a hang is not only a fault until the probe proves otherwise. So:
- **Watchdog.** If an unlocked, connected session has a running probe, but the service accepted no line from it for 30 seconds (three times the longest interval of D4), the service ends the probe with `TerminateProcess`. The end of the probe closes the write end, so the blocking `ReadFile` of the reader thread (D3) returns with `ERROR_BROKEN_PIPE` and the thread ends. The 30 seconds start again at each unlock, connect and resume (S20, see "Sleep and resume" below).
- **Restart after the delay.** An end that the service did not ask for is a crash, an exit after a failed restore of the thread desktop (D4 step 8), an exit for another reason, or a watchdog kill. After each such end, the `RegisteredWaitHandle` callback of step 8 starts a new probe after a delay of 1 second after the first such end of the session, then 2 seconds, then 5 seconds for each further one within 10 minutes. So a new probe runs within 10 seconds after the end. The delays count per session and logon: a `WTS_SESSION_LOGON` starts a new count. The service skips the start if the session got `WTS_SESSION_LOGOFF` or is gone (below). The tick stays as a second path with the same skip. It does not wait for the classification below.
- **An end that the service asked for** (at `WTS_SESSION_LOGOFF`, at the service stop, or because the pipe broke at a service end) is no fault and is not classified.
- **No reset of the gap (S15).** After an end that the service did not ask for, `ForegroundSampleCounter` (D5) keeps the last-sample time of the session. The first sample of the new probe gets the time since the last accepted sample of the old probe under the gap rule of D5, not zero. Both probes read the same system-wide `GetTickCount64`, so the `t` values stay comparable. Without this rule, a crash that the child triggers before the second sample of each run would count nothing.
- **Count the unexpected ends.** D6 says what the counter does: from the 3rd unexpected end within 10 minutes, each one is a budget item (D6a, never the strike; N26), and the 3rd within one hour alerts the parent.

**The end of a probe at a sign-out (spike 1.4).** *Decided by the orchestrator under the user's delegation (2026-11-27).* The spike showed that Windows ends the SYSTEM probe during a sign-out before the service knows about the sign-out. `Kid` signed out with `shutdown /l`, and the session was gone from `query session` after about 7 seconds. Windows ended the probe (exit code 0x40010004, `DBG_TERMINATE_PROCESS`) 6 seconds before `WTS_SESSION_LOGOFF` reached the service. The 60-second tick then started a new probe in the ending session, and Windows ended it 0.3 seconds before the notification. Under the old rules, one honest sign-out gave 2 unexpected ends, and two sign-outs within one hour reached the alert.

*Revised by the orchestrator under the user's delegation (2026-11-27, review decisions).* The first fold-in of the spike waited 15 seconds after an end before any restart. The review found that this wait is not needed: spike 1.4 showed that Windows also ends the second probe in an ending session, and the sign-out still completes in normal time. The wait only added time without samples after a real crash. So the service restarts after the normal delays and classifies the end later:
- After each end that the service did not ask for, the service restarts the probe after the delays above, at once, without a wait.
- **The end wait.** For 90 seconds of unbiased time after such an end, the service watches the session. If `WTS_SESSION_LOGOFF` for that session, a gone session, or a stop of the service (the stop or the shutdown control, and the preshutdown control if task 4.2 adds it) comes in that time, the end is a **session-end end**: it needs no new probe and gives no `PROBE_RESTART` event, no alert and no budget item.
- **A benign end** is an end within 15 seconds after a resume (the resume window, S20, see "Sleep and resume" below): the service restarts the probe at once, without a delay, and the end gives no event and no item. It does not count for the restart delays.
- Each other end is an **unexpected end**. Only at the end of the end wait does the service write `PROBE_RESTART`, count the end for the alert, and add the budget item of D6. A watchdog kill goes through the same end wait, because a probe can also hang while its session ends.
- The service queries the session state of N23 at the end itself and keeps it. The budget item of an unexpected end counts only if that state was active and unlocked.
- The service never starts a probe in a session after its `WTS_SESSION_LOGOFF` or in a session that is gone: not from the wait callback, the tick, an unlock or a resume.
- Only facts of the service decide: the WTS notifications, the WTS queries and the service controls. The `sessionEnding` message of the Agent Channel does not decide the class of an end, because the child can make its agent send it at any time (D8, `CLAUDE.md`). It starts only the Lock Deferral and the hold or the guard, as D8 states.

**The sign-out state (review decision).** The service keeps "got `WTS_SESSION_LOGOFF`" per session ID and logon, not per session ID alone, because Windows reuses session IDs. The logon is the logon time of the session (`WTSQuerySessionInformationW(WTSSessionInfo)`, `LogonTime`). A `WTS_SESSION_LOGON` clears the state of that session ID. A session is gone only if both `WTSQuerySessionInformationW` fails and `WTSEnumerateSessionsW` does not list it. "Gone" is never kept: each tick and each start checks it again. So a failed query in a living session does not stop the probe for the rest of the session.

Why 90 seconds: the measured sign-out took about 7 seconds, and the first end came 6 seconds before the notification. A sign-out can take much longer if a program asks to save ("apps prevent sign-out"): the child can then wait before it clicks "Sign out anyway" or Cancel. 90 seconds covers a slow sign-out with a large margin. The end wait does not delay the restart, so a longer wait costs no sample time; it only delays the event and the budget item of a real crash. The service lifetime (`ParentalControlServiceLifetime`) handles only the session and the power events today. So task 4.2 makes sure that the service sees a shutdown (the shutdown control, and the preshutdown control if the order needs it) and records its order against the end of the probe. The service logs the exit code of each end of a probe.

The cost: a probe that the service restarts in an ending session can start and end again before `WTS_SESSION_LOGOFF`. Spike 1.4 showed one such probe; Windows ended it, and the sign-out completed. Each of these ends is a session-end end. The delays of 1, 2 and 5 seconds bound the number of starts in one sign-out. Tasks 4.2 and 9.1 check a sign-out with unsaved work in Notepad. A risk is not measured yet: if Windows also ends each new probe while it shows that apps prevent the sign-out, a long wait at that screen followed by Cancel gives several ends that become unexpected ends, and from the 3rd ones budget items. This is a named gate of task 4.2: more than 2 probe ends during that screen is a failed check, and `/opsx:update` must decide a rule before task 4.5 or 4.7 can turn the probe locks on.

Rejected alternatives:
- **The exit code 0x40010004 as the sign of a sign-out.** The docs do not name it as the code of a sign-out, and the code alone does not show that the session ends.
- **The `sessionEnding` message of the agent.** It is agent data.
- **A wait of 15 seconds before the restart** (the first fold-in of spike 1.4). It adds time without samples after each real crash, and spike 1.4 showed that a probe in an ending session does no harm.
- **The connect state at the end.** The spike did not record it, and the end comes before the notification.

**Sleep and resume (S20).** Re-review 4 showed that the watchdog and the kept gap of S15 ignored sleep. If the PC resumes without a sign-in screen (a child account without a password, or no sign-in on wake), the session stays unlocked and `WTSActive`. The clock of the service then shows more than 30 seconds since the last accepted line, before the probe has sampled again. The watchdog killed a healthy probe, wrote `PROBE_RESTART`, and from the 3rd lid close in 10 minutes added budget items. `ProbeOutageMonitor` saw an outage after a long sleep, and the kept gap charged up to 12 seconds of sleep. So the service treats a resume like an unlock:
- The service already gets the power events (`ParentalControlServiceLifetime.OnPowerEvent`, `SERVICE_CONTROL_POWEREVENT`). At `PBT_APMSUSPEND` it stops the watchdog and the outage timer of each session. At `PBT_APMRESUMEAUTOMATIC`, which Windows "always sends ... whenever the system resumes" (`WM_POWERBROADCAST`), and at `PBT_APMRESUMESUSPEND`, it starts the 30 seconds and the 5 minutes again.
- The first sample of each session after a resume counts as the first sample after a planned start: it adds zero (D5). This loses at most one interval of honest time per resume.
- An end of a probe within 15 seconds after a resume (the resume window) is a benign end: a new probe starts at once, and the end gives no `PROBE_RESTART` event and no budget item.
- Sleep time does not count in a window of 10 minutes of unlocked time (D5, D6, D6a).
- A backstop that does not need the power event: the watchdog and the outage timer measure with `QueryUnbiasedInterruptTime`, which "does not include time the system spends in sleep or hibernation". At each accepted line the service also keeps the unbiased time. If the `t` delta (`GetTickCount64`) of a line is more than 1 second larger than the unbiased delta, the system slept, and the service handles the line as the first sample after a resume. So a late or missing power event, or a probe line that arrives before it, does no harm.

The `GetTickCount64` page does not say whether the count includes sleep. Task 1.6 records it with the unbiased delta, the order of the power events against the first probe line, and the behaviour on Modern Standby if the child's PC uses it (task 1.7). The Modern Standby page of Microsoft was not available for this revision, so the design claims nothing about it; the unbiased backstop is the named fallback.

Rejected alternatives:
- **Native AOT for the probe** (no .NET runtime in the process at all). It is a stronger option, but AOT cannot cross-compile from the Mac, and `build.ps1` and CI need a separate publish step. A later change can add it.
- **A probe in C or C++.** A second toolchain for one small program.
- **A probe with all SYSTEM privileges.** It needs none, and each privilege makes a bug in the probe worse.
- **A framework-dependent probe** (the first draft). It contradicts `build.ps1` and adds a runtime search.
- **Only the probe on .NET 10, the rest on .NET 8.** It works, but all parts are out of support, CI and the VM need two SDKs anyway, and the chore is small.
- **A Job Object with kill-on-close** (the first revisions, N17). A job in session 0 cannot hold a process of another session, so the step always fails.
- **`CREATE_NO_WINDOW`** (the first revisions, S13). It still starts a hidden console host.
- **`REALTIME_PRIORITY_CLASS` for the probe** (N12). The service could set it, but a bug in a realtime SYSTEM process can freeze the PC of the child. Time-critical in the High class is enough to get a turn.

### D3. The probe sends window handles and ids through an anonymous pipe
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for B2, S7, N1, for B3, S9, N15, N19, for B5, for the ghost window of spike 1.2, and for the sample time of the review decisions).*

The service creates an anonymous pipe with `CreatePipe` and an explicit security descriptor for SYSTEM only (N1). `CreatePipe` makes a named pipe with a unique name and one instance. Without the explicit descriptor, the DACL comes from the token of the creator; the explicit descriptor removes this dependency. The probe inherits only the write end (D2) and gets its handle value on the command line. The child cannot open the pipe, and it cannot create a second instance.

The probe opens no process (B2). The child owns its game process and can remove SYSTEM from its DACL with no code; a probe without privileges then fails at `OpenProcess`. So the probe sends only what it reads from the window manager, and the service reads the process itself (D3b).

Format: one line of UTF-8 JSON per sample, at most 4 KB. Each sample line has `t`, the `GetTickCount64` value of the probe at the sample (S9), and `dur`, the duration of the sample in milliseconds.

**The time of a sample (review decision).** *Decided by the orchestrator under the user's delegation (2026-11-27).* The probe reads `t` directly after it reads the Foreground Window (D4 step 3), so `t` is the time of the state that the sample shows, also if an earlier call of the sample stalled. A blind sample of step 1 or 2 reads `t` at the failure. `dur` is the time from the start of step 1 to the end of step 7, from `GetTickCount64`. The spike showed one sample that took 24.2 seconds under CPU load (task 1.5), so the time of a sample is not always short. D5 says how the service uses `dur`. A line without a valid `dur` counts as a sample with a `dur` of 0, with a log line at most once per probe run.

Kinds:
- A window in front: `{ "t": 123, "dur": 4, "fg": { "hwnd": 1, "tid": 2, "pid": 3 }, "focus": { ... }, "children": [ { ... } ], "cursor": { "noActivate": true, "entries": [ { ... } ] }, "title": "...", "desktop": "..." }`. Each entry has `hwnd`, `tid` and `pid`. Only `fg` is required. The entries (D4):
  - `fg`: the Foreground Window.
  - `focus`: the window with the keyboard focus from `GetGUIThreadInfo`, only if its process differs from `fg`.
  - `children`: one visible child window of each other process below the `fg` window, at most 8 processes (B3). This replaces the `frame` entry of the first revisions (the first child of an `ApplicationFrameWindow`).
  - `hung`: only if the `fg` window is a ghost window: the hung window that the ghost replaces (D4 step 3).
  - `cursor`: the window under the cursor and its parent windows up to the top-level window (B5). `entries` has one entry for each process on that chain that differs from `fg` and from each entry above, at most 8. `noActivate` is true if the top-level window of the chain has the style `WS_EX_NOACTIVATE` (B3, B5). The probe leaves out `cursor` if `entries` is empty.
- No window in front (`GetForegroundWindow` returns NULL): `{ "t": 123, "window": false }`.
- A blind sample: `{ "t": 123, "blind": "desktop" }` (the input desktop cannot be opened or set), `{ "t": 123, "blind": "window" }` (a window is in front, but `GetWindowThreadProcessId` gives no thread after one retry), or `{ "t": 123, "blind": "children" }` (more than 8 other processes have visible windows below `fg`). A found window never gives an empty `fg`.
- A log line: `{ "log": "..." }`, at most 256 characters, at most one per minute.

The window title and the desktop name come from programs of the child. The probe cuts the title at 256 and the name at 64 UTF-16 characters, and replaces each lone surrogate and each control character with U+FFFD before it serializes them. An entry has three numbers, and a sample has at most 1 + 1 + 1 + 8 + 8 entries. So a line is always much shorter than 4 KB.

The service reads the pipe with a fixed buffer of 4 KB per line (S7), not with `StreamReader.ReadLine`: it drops a line that is longer, up to the next line end, without a larger buffer. A line over 4 KB, a line that does not parse, a sample line without a valid `t`, or a field with a wrong type drops only that one line or that field, with a log line at most once per probe run. Content never ends the probe: else a program of the child could cause a probe outage (D6) with a strange title.

**One blocking reader thread per probe (N19, S9).** Anonymous pipes do not support overlapped I/O (Microsoft Learn, "Anonymous Pipe Operations"), so the service cannot reuse the asynchronous path of the Agent Channel (D7). It reads each probe pipe on its own dedicated thread with a blocking `ReadFile`, at `THREAD_PRIORITY_TIME_CRITICAL`. The same thread reads the entries of the sample (D3b) at once, so the window has little time to go away, and then gives the result to the counting. The thread ends when the pipe breaks.

**The sample time is the time of the probe (S9).** The first revisions used the receipt time of the service. A child that loads all cores delays the service reader, and the queued lines then got receipt times close together, so the counter added less than the real time. Now the service uses `t`. `GetTickCount64` is a system-wide counter, so the probe and the service read the same clock. The probe is SYSTEM code, so its clock is not a child input. The service checks `t`: it must be larger than the `t` of the previous line of the same probe run, and not larger than the current `Environment.TickCount64` of the service. Else the service drops the line as a bug.

**Which lines move the last-sample time (N15).** Each sample line that the service accepts (a window in front, `window: false`, a blind sample) moves the last-sample time of the session to its `t`. Only read entries (D3b) add time. A dropped line moves nothing: it is no sample, so the next accepted sample gets the time since the last accepted sample under the gap rule of D5. The probe is SYSTEM code, so a dropped line is a bug, not a child action, and the gap rule bounds its effect.

### D3b. The service reads the process of a sample, and fails closed if it cannot (B2)
*Decided by the orchestrator under the user's delegation (2026-11-27; revised 2026-11-27 for B3, S9, N15, and for S14).*

At its start the service enables `SeDebugPrivilege` in its own token (`AdjustTokenPrivileges`). The LocalSystem token has the privilege, and Microsoft lists it as enabled, but the service does not rely on that. With it, `OpenProcess` grants the access "regardless of the contents of the security descriptor" (OpenProcess docs), so a DACL that the child sets on its game does not stop the service. If the enable fails, the service logs an error and sends one alert per day. `ProcessControl.ListProcesses`, the suspension and the Blocked Start check use the same token, so this also closes the hole that a game with a hostile DACL is left out of the process list.

For each entry (`fg`, `focus`, each of `children`, each of `cursor.entries`, and `hung` when the ghost rule of D4 uses it) of a sample the service does:
1. `OpenThread(THREAD_QUERY_LIMITED_INFORMATION, tid)` and `GetProcessIdOfThread` must give `pid`. The probe read `tid` and `pid` from the same window at the same time, so this ties the window to the process at the time of the sample and guards against pid reuse.
2. `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, pid)`, `ProcessIdToSessionId`, `QueryFullProcessImageNameW`, `GetProcessTimes`. The session must be the session of the probe.

**No start-time test after a passed thread test (S14).** The first revisions also required a start time before `t`, and called a later start time Unreadable. Re-review 3 showed two faults. A later start time does not mean a child action: it means a reused pid, so the sampled process ended. And `GetProcessTimes` gives a wall-clock FILETIME, while `t` is `GetTickCount64`, so the comparison needs a conversion, and a step of the system clock (w32time, or a wrong RTC at boot) makes an honest start time look "after" `t`. Each such entry then fed the budget or the strike, a false lock. The thread test of step 1 already excludes a reuse: if thread `tid` still exists and belongs to `pid`, a mix-up needs both the thread ID and the pid to be reused into each other between the sample and the read, a few milliseconds later. So the service does no start-time test for the outcome. It keeps the start time for the suspension, and it logs a start time more than 1 second after the converted `t` at most once per probe run, as a sign of a clock step. A standard user cannot set the system clock; it can only change the time zone, which does not change a FILETIME.

The first revisions also checked that the exe of `fg` is `System32\ApplicationFrameHost.exe` before they used `frame`, because the child can register a window class with the name `ApplicationFrameWindow`. That check goes: each visible child window of another process is an entry now (B3), whatever the class of `fg` is. A fake `ApplicationFrameWindow` of a game makes the game `fg`, so the game counts, and a Study child window in it counts too (fail closed).

Outcomes of an entry:
- **Read:** the service has the exe path and the start time.
- **Ended:** the thread or the process does not exist any more (`ERROR_INVALID_PARAMETER` from `OpenThread` or `OpenProcess`), or the thread now belongs to another process (S14: the thread ended and Windows reused its ID). The window closed between the sample and the read. That entry counts no time; the other entries of the sample count. An Ended entry in a role that would count time goes into the blind budget of D6a, but it does not trigger the strike (S9, S14). These roles are `fg`, `focus`, each child entry, and each `cursor` entry when `noActivate` is true. So a child who delays the service and re-creates its game window on a new thread before each read gets no free time, also for an embedded game or a `WS_EX_NOACTIVATE` game (S14). An honest window close, which the time-critical reader makes rare, cannot lock the child at once. A sample adds at most one item to the budget, whatever the number of its Ended entries. A `cursor` entry without `noActivate` that ended adds nothing, because the cursor passes over windows that close often. Task 1.2 records how often honest entries end in each role.
- **Unreadable:** access denied, or a process of another session. The sample is a blind sample (D6a). `SeDebugPrivilege` gives the service `PROCESS_QUERY_LIMITED_INFORMATION` and `THREAD_QUERY_LIMITED_INFORMATION` for each process, and the access rights page of Microsoft does not list `PROCESS_QUERY_LIMITED_INFORMATION` among the rights that a protected process denies. A window of the input desktop belongs to a process of that session. So this outcome means a child action or a bug, and it fails closed.

If one entry is Unreadable and another entry is Read, the Read entries still count and the sample is also blind (N15). Both sides fail closed.

### D4. Sampling in the probe
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for S6, S8, N4, for B3, N11, N12, for B5, for N28, for the ghost window and the lock state of spike 1.2, and for the ghost fallback of the review decisions).*

The sampler thread of the probe (MTA, never a window or a hook) does this for each sample:
1. `OpenInputDesktop(0, false, DESKTOP_READOBJECTS)`. If it fails, the sample is `{ "blind": "desktop" }`.
2. `SetThreadDesktop` to that desktop. So the probe follows a desktop that the child created and switched to. A desktop that a tool such as Sysinternals Desktops creates gets the default DACL of the child's token, which gives SYSTEM full access. A desktop that the child creates with its own security descriptor can deny SYSTEM; then step 1 or 2 fails, and the sample is blind (D6a). `GetUserObjectInformationW(UOI_NAME)` gives the name for the log only. The probe has no rule by desktop name: the child chooses the names of its own desktops.
3. `GetForegroundWindow`, then `GetTickCount64` for `t` (D3). If it gives NULL, the sample is `{ "window": false }`. Else `GetWindowThreadProcessId`; if it gives no thread, the probe tries step 3 once more, and then sends `{ "blind": "window" }`. If `GetClassNameW` of the `fg` window gives `Ghost`, the probe calls `HungWindowFromGhostWindow(fg)`. If that gives a window and `IsHungAppWindow` gives true for it, the sample gets `hung` with the ids of that window (see "The ghost window of a hung program" below). `GetClassNameW` reads the stored class and sends no message.
4. `GetGUIThreadInfo(0, ...)` gives `hwndFocus` of the foreground thread (S6). If it is not NULL and `GetWindowThreadProcessId(hwndFocus)` gives another process than the Foreground Window, the sample gets `focus`. A window of another process can have the focus if the child put it into a foreign window with `SetParent`, or with `AttachThreadInput`.
5. `EnumChildWindows(fg)` visits all descendant windows of the Foreground Window (B3). For each window that `IsWindowVisible` accepts and that has a non-empty rectangle, the probe takes the process from `GetWindowThreadProcessId`. Each process other than the `fg` process gives one entry in `children` (the first visible window of that process). If more than 8 other processes have such windows, the sample is `{ "blind": "children" }`: a cut list would let the child hide a game behind 8 decoy windows. The probe stops the walk after 4096 windows and then also sends `{ "blind": "children" }`. A Store app is the normal case: `fg` is `ApplicationFrameHost.exe` and the app window is a child. The Store-app code of the agent `ActivityTracker` moves into the probe project in this form.
6. `GetCursorPos` and `WindowFromPoint` give the window under the cursor (B3). This can be a child window. The `WindowFromPoint` page does not say so in words, but its note that for a static text control it returns "the window under the static text control" implies that it returns other child controls; task 1.2 confirms it. The probe walks from that window up with `GetAncestor(GA_PARENT)` (the parent, not the owner) to the top-level window, which it gets with `GetAncestor(GA_ROOT)`, at most 32 steps (B5). It takes the process of each window on that chain with `GetWindowThreadProcessId`. The hit window and the top-level window come first; then the other windows from the bottom up. Each process that differs from `fg` and from each entry of steps 4 and 5 gives one entry in `cursor.entries`, at most 8. `noActivate` is true if `GetWindowLongPtrW(GWL_EXSTYLE)` of the top-level window has `WS_EX_NOACTIVATE`. The chain of an honest window has one to three processes. The cut after 8 processes or 32 steps makes no blind sample, so it adds no false lock; it can only drop a process in the middle of a chain that a script built, which D13 accepts. `GetCursorPos` needs the input desktop as the thread desktop, which step 2 sets. `WindowFromPoint` skips hidden and disabled windows; a game in such a window gets no mouse input. `GetAncestor` and `GetWindowLongPtrW` send no message. The `WindowFromPoint` page does not say whether it sends `WM_NCHITTEST` to a window of another thread, so a hung window under the cursor could block the sampler (N28). Since S15, a stall is not harmless: a watchdog kill is an unexpected end. Task 1.2 checks a hung window under a resting cursor while another window is `fg` and records the largest sample gap. The named fallback: step 6 runs on one helper thread of the probe with a timeout of 1 second; on a timeout the sample has no `cursor` (never blind), and the probe starts no new cursor call until the stuck one returns.
7. `GetWindowTextW` of `fg`, at most 256 characters. For a window of another process, this reads the stored caption and sends no message, so a hung window cannot block the probe. `EnumChildWindows`, `IsWindowVisible`, `GetWindowRect` and `GetWindowThreadProcessId` in step 5 send no message either; for `WindowFromPoint` in step 6, see N28 above.
8. `SetThreadDesktop` back to the original desktop of the thread (from `GetThreadDesktop` at the start), then `CloseDesktop` on the handle of step 1 (S8). `CloseDesktop` fails while a thread of the process uses the desktop, so the order matters; else the probe leaks one desktop handle per sample. If the restore fails, the probe exits; the service starts a new one (D6).

**The lock state comes from the lock notification (spike 1.2).** *Decided by the orchestrator under the user's delegation (2026-11-27).* The service takes the locked state of a session from `SessionTracker`: the WTS lock and unlock notifications, and at the service start the lock flag of Windows (`SessionManager.QueryLockFlag`). It never derives the lock from the windows or the desktop of a sample. The spike showed that the lock curtain after Win+L is on the desktop `Default` with `LockApp.exe` in front, while the connect state stays `WTSActive`. Only Ctrl+Alt+Del shows the desktop `Winlogon` with `LogonUI.exe`. While the session is locked, nothing counts and no item counts (D6a, N23). `LockApp.exe` is below the Windows folder and so in System, so a sample of the curtain counts nothing in any case. On the secure desktop of UAC, `consent.exe` is in front, which is below the Windows folder and so in System. Task 1.5 checks that UAC, Ctrl+Alt+Del, the secure screen saver and a fast user switch give no blind sample.

**The ghost window of a hung program (spikes 1.2 and 1.5).** *Decided by the orchestrator under the user's delegation (2026-11-27).* If a program stops responding, Windows replaces its top-level window with a ghost window of `dwm.exe` (class `Ghost`). The spike read `fg` = `dwm.exe` for a hung program, so its time counted as System. Under the CPU load of task 1.5, a starved game became a ghost window in 15 of 49 samples, and its time went to `dwm.exe`. So:
- The probe resolves the ghost window in step 3 and sends the hung window as `hung`. Only the probe can do this, because session 0 cannot call window functions for another session (D1).
- The service uses `hung` only if the Read `fg` is `%SystemRoot%\System32\dwm.exe`. Then it reads `hung` as D3b states and uses it in the role `fg` instead of the ghost window. If `fg` is another exe, the service ignores `hung`. A child can register a window class with the name `Ghost`, but it cannot run code in `dwm.exe` (it runs as `Window Manager\DWM-n`), so this check is enough.
- The read of `hung` follows D3b in the role `fg`: an Unreadable `hung` makes the sample blind, and an Ended `hung` is a budget item. *Decided by the orchestrator under the user's delegation (2026-11-27, review decision):* the fallback below is only for a missing `hung`, because a child that denies SYSTEM on its hung game must not get the category of the last sample instead of a blind sample.
- If the sample has no `hung` and the Read `fg` is `%SystemRoot%\System32\dwm.exe`, the service keeps the category of the last sample of that window: it uses the `fg` process of the last accepted sample of the session that was not a ghost, if that process still runs (the same pid and start time). Else the ghost window counts as System, as before. This fallback is no blind sample and no budget item, because the ghost window itself was Read.
- A game that the service suspended stops to respond, and Windows can show a ghost window for it. The ghost window resolves to the suspended exe, which counts nothing (`category-limits`, scenario "Suspended game in front").
- The ghost rule applies to `fg` only. A ghost window under the cursor or below `fg` stays `dwm.exe` (System).

`IsHungAppWindow` is documented. The design does not rely on public docs for `HungWindowFromGhostWindow`, an export of `user32.dll`, so task 4.1 proves it on the VM. If it does not work, the fallback of the service above still applies.

**Why the children and the cursor (B3).** The first revisions counted `fg`, `focus` and the first foreign child of a Store app frame. Re-review 2 showed that a script can put an unchanged game into `notepad.exe` with `SetParent` (AutoHotkey `DllCall` or PowerShell `Add-Type` is enough). A click on the embedded game activates Notepad, and Notepad gives the focus back to its edit control, so `fg` and `focus` are both Notepad (System) and nothing counted. Step 5 closes this: each visible window of another process below `fg` is an entry. The script can also set `WS_EX_NOACTIVATE` on a top-level game window from outside (`SetWindowLongPtrW(GWL_EXSTYLE)` works across processes at the same integrity level). Then a click on the game does not make it the Foreground Window. Step 6 closes this for a mouse-driven game: the cursor is over the game while the child plays. D5 decides which `cursor` entries count.

**Why the chain under the cursor (B5).** Re-review 3 combined the two techniques of B3: a script puts the game into Notepad with `SetParent` and then sets `WS_EX_NOACTIVATE` on the Notepad window. The `WM_MOUSEACTIVATE` page says that `DefWindowProc` "passes the message to a child window's parent window before any processing occurs", and the extended styles page says that a top-level window with `WS_EX_NOACTIVATE` "does not become the foreground window when the user clicks it". So Notepad never becomes `fg`, and the walk of step 5 never visits the game. The first revisions reduced the hit window to its top-level window (Notepad, System) and lost the game. Step 6 now keeps the process of the hit window (the game) and of each window on its parent chain, and reads `noActivate` from the top-level window (Notepad). The docs do not describe a click on a child of a `WS_EX_NOACTIVATE` top-level window, so task 1.2 confirms the attack. If Notepad does become `fg` there, step 5 already covers the case. The fix is cheap, and its counting depends on a `WS_EX_NOACTIVATE` top-level window under the cursor, which is rare in honest use (D5).

**The sample times are random (N4, N11).** The child can read the CPU time of the probe in Task Manager or with `NtQuerySystemInformation`, so it can see when a sample happens. With a fixed interval it could switch to a hidden desktop or another window right after each sample and come back before the next one. So the probe waits 0.2 seconds plus an exponential random time with a mean of 4.8 seconds, at most 10 seconds in total, before each sample. It takes the random numbers from `RandomNumberGenerator`. After the first 0.2 seconds, the time to the next sample does not depend on the time that passed. So the share of samples that see the hidden state is the share of time in that state, and the budget of D6a holds. The first revisions used a minimum of 1 second. Re-review 2 showed that a child who sees each sample could then show the game for about 0.9 seconds after each one without a blind sample (about 20 % of the time). With 0.2 seconds this safe window is about 4 % of the time, and the extra CPU cost is small.

### D5. Counting from samples
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for S1, S5, S6, for B3, B4, S9, S10, N14, N16, for B5, S15, S16, N22, for B6, S20, S21, S22, for the gap rule of spike 1.5, and for the review decisions on the gap rule).*

A pure class `ForegroundSampleCounter` (Domain) keeps, per session, the sample time `t` of the last accepted sample (D3) and its counted exes (see "The sameness test" below). For each sample it returns the seconds to add under the gap rule below. It returns zero, and no item, for the first sample after a planned probe start (sign-in, unlock, connect, service start) and for the first sample after a resume from sleep or hibernation (S20, D2). After an end of a probe that the service did not ask for (D2), it keeps the last-sample time, so the gap rule also applies to the gap over the restart (S15). D3 says which lines move the last-sample time (N15).

**The gap rule (spike 1.5).** *Decided by the orchestrator under the user's delegation (2026-11-27; revised the same day for the review decisions on the sameness test, the sample time and the gap over a probe end).* The gap is the time since the last accepted sample of the session.
- A gap of 12 seconds or less (the longest interval of D4 plus a margin) goes to each category of the counted processes of the sample, as before.
- A gap of more than 12 seconds goes in full, at most 60 seconds, to each category of the counted processes of the new sample if neither sample is a blind sample and both samples are the same under the sameness test below. Two samples with no counted exe (System only, or `window: false`) are the same too; they add nothing.
- Each other gap of more than 12 seconds adds 12 seconds to the counted processes of the new sample, and the gap is one budget item of D6a, never the strike.
- A gap of more than 60 seconds is also one budget item, also if both samples are the same.
- **A long sample.** If the `dur` of the new sample (D3) is more than 12 seconds, the gap that ends at it adds at most 12 seconds and is one budget item, also if both samples are the same. A stall inside the sample hides what was in front during the stall.
- **A gap over a probe end.** A gap that spans an end of a probe that the service did not ask for (D2) is no gap item, and its long-sample rule gives no item either. The end itself counts as D6 states, if it is an unexpected end. The time follows the rules above: in full, at most 60 seconds, if both samples are the same, else 12 seconds.
- A sample adds at most one budget item: a gap item and an Ended item of D3b in one sample are one item. A blind sample stays a blind sample.
- The first sample after a planned start or a resume adds zero and no item, and so does a line that the unbiased backstop of D2 marks as after a sleep. N23 decides whether an item of a locked or not active session counts.

**The sameness test (review decision).** *Decided by the orchestrator under the user's delegation (2026-11-27).* Two samples are the same if they have the same set of counted exes: for each counted process of `fg`, `focus` and `children` (after the ghost rule of D4 and the creator rule below), its exe path, which the App Rules match, and its category. The test leaves out the `cursor` entries, also those with `noActivate`. The first fold-in compared the pid, the start time and the category. Reasons for the change:
- The exe and the category are what a limit charges. A pid and a start time add nothing that the child cannot also control, and a game that restarts during a gap is still the same game.
- The cursor moves in honest use. With the cursor entries in the test, a gap in which the child only moved the mouse over another `noActivate` window would be a budget item.

**The event of a gap (review decision).** The service writes the event `PROBE_GAP` (new value of `EventType`) for each gap of more than 12 seconds and for each long sample, with the gap, `dur` and whether it counted in full. A gap over a probe end writes no `PROBE_GAP`, because the end has its own event. The service sends the parent at most one Telegram alert per Restricted User and day (the Control Time Zone, D14) for these events. A gap never locks the session by itself; only its budget item counts toward the lock of D6a. The event and the alert are not probe locks, so the shadow mode (D12) does not change them.

Why: under the CPU load of task 1.5 on VM 102, the gaps reached 34.2 seconds, and the 12-second cap counted 141 of 300 seconds of play. The cap failed open. The new rule counts the gap where both samples show the same programs, and fails closed (a budget item) where they do not. So counting never undercounts a game by design, within the bound. The orchestrator named "the foreground"; the rule takes all counted processes, so that a game inside a System window (B3) also gets its gap. In the plain case the only counted process is the foreground.

Why 60 seconds: the bound must cover each gap that the design itself makes, with a margin.
- The measured CPU-load gap: 34.2 seconds.
- A watchdog kill (30 seconds), a restart delay of up to 5 seconds, the start of the probe (spike 1.6: 6.1 seconds from the kill to the first line, with a delay of 1 second), and one interval of up to 10 seconds: about 47 seconds.
- A crash up to 10 seconds after the last sample, a delay of up to 5 seconds, the start, and one interval: about 31 seconds. The end wait of D2 does not delay the restart.
60 seconds covers each case. It also bounds the time that a fault adds to one minute per gap.

A CPU load that stalls the probe for more than 30 seconds gives a watchdog kill. If the session does not end within the end wait, that is an unexpected end (D2): a `PROBE_RESTART` event and, from the 3rd within 10 minutes, a budget item. The gap rule spans the restart, so the time still counts if the same programs are in front. Task 9.1 records the watchdog kills under load on the child's PC.

**The counted processes of a sample.** A pure class `CountedProcesses` (Domain) takes the Read entries (D3b) and decides:
1. `fg`, `focus` and each entry of `children` count, except each one in System (S6, B3).
2. The `cursor` entries count only if `noActivate` is true, each one except in System (B3, B5). So a game inside a System window with `WS_EX_NOACTIVATE` counts while the cursor is over it. A `cursor` entry without `noActivate` counts no time, but its exe becomes a suspend candidate (step 6).
3. A trusted WebView2 process counts, in each role, as the program that started it (S16). The service follows the parent pids from the `msedgewebview2.exe` (`ProcessControl.QueryParentPid`, which the Blocked Start code already uses) to the first process that is not a trusted WebView2, at most 4 steps, and treats that creator as the entry in the same role: `fg`, `focus` and a child count by the rule of the creator, a `cursor` entry only with `noActivate`. A trusted WebView2 process is an exe with the file name `msedgewebview2.exe` below `%ProgramFiles(x86)%\Microsoft\EdgeWebView\Application\` or `%ProgramFiles%\Microsoft\EdgeWebView\Application\`, the folders of the Evergreen WebView2 Runtime, which only administrators can change. Details below.
4. Each other `msedgewebview2.exe` is an ordinary exe: it counts by its App Rule like any other exe (B4).
5. The Session Agent counts in Unknown, whatever the App Rules say, as `fg`, `focus` or a child entry (S1, N22). The agent is never a child window in honest use, so this costs nothing, and a script that moves an agent with a game drawn in it into Notepad still counts. As a `cursor` entry it counts nothing, so a cursor over the widget costs nothing. While the service has an active Interactive Session Prompt for that user, the agent counts nothing at all (S10). Else the Agent Window Budget (below) exempts its entry for at most 5 minutes in 60 minutes of unlocked time.
6. The service adds the interval to the category of each counted process, at most once per category. It records in `ForegroundHistory` the exe of each Read entry, also of a `cursor` entry without `noActivate`, and the creator of each trusted WebView2 entry. So each sampled exe and each WebView2 creator is a suspend candidate.

**The creator of a trusted WebView2 (S16).** Re-review 3 showed two faults of the old rule ("a trusted WebView2 counts with the Foreground Window"). A script can move the WebView2 child window of any WebView2 app into `notepad.exe`; the host `fg` is then System, so nothing counted and nothing was a suspend candidate. And a trusted `msedgewebview2.exe` can be `fg` itself: the WebView2 reference says that a new window opens "on a popup window" if the app does not handle the `NewWindowRequested` event. Under the old rule that popup counted as itself (Unknown) and is never suspended, so a login or help popup of a Study app locked the session after 60 seconds while Unknown was exhausted. The creator rule fixes both: the moved control counts as its app, and the popup counts as the Study app. The WebView2 shell flyouts still count nothing, because their creator `explorer.exe` is System.

The parent chain of a WebView2 process is the host app, then the WebView2 browser process, then its child processes. Outcomes:
- **Read:** each step finds a parent that runs and that started before its child (`GetProcessTimes`; a parent that started later has a reused pid). The creator counts.
- **Not attributed:** a parent on the chain does not run any more (S21), the start-time test fails, the chain has more than 4 steps, or a parent is in another session. The entry counts nothing, it is no blind sample and no budget item, and the service logs it at most once per probe run. A clock step can make an honest parent look younger than its child (the trap of S14), and a blind sample here would lock.

There is no Ended outcome for the chain (S21). Re-review 4 showed that a parent that ended can be a lasting state, not a race. WebView2 controls with the same user data folder share one browser process, also across app processes ("If you launch two copies of your host app, they will use the same UDF"; the default folder is derived from the exe). If the first instance of an app started the browser process and the child closes that instance, the browser process can live on for the second instance, and its recorded parent is gone. As a budget item, each sample with that WebView2 in front would feed the budget and lock in about 30 seconds. So a parent that ended is "not attributed". The Ended outcome of D3b still applies to the thread and the process of the `msedgewebview2.exe` entry itself: if that entry ended between the sample and the read, it is a budget item as in D3b.

The cost of "not attributed" (S21): a WebView2 popup of the second instance of a Games app, in front as `fg`, counts nothing, without a script. The main window of that instance still counts as `fg` or as the host of the control, and the app is a suspend candidate. This needs an app that the child runs twice, a closed first instance, and play inside a popup window; it is accepted. Task 1.2 records the chain of a second instance. The named fallback if the spike shows that it is common: the service keeps the creator exe of each browser process (pid and start time) while its chain was Read, and uses that exe when the parent ended later. The default user data folder belongs to one exe, so the kept exe is the right app.

Rejected for S21: **a not-attributed `fg` WebView2 counts in Unknown** under the rule of a program that is never suspended. This brings back the lock of an honest popup of a Study app while Unknown is exhausted, which S16 removed.

A child can reach "not attributed" with a script that starts a WebView2 process itself (D13).

`QueryParentPid` uses `NtQueryInformationProcess(ProcessBasicInformation)` with `PROCESS_QUERY_LIMITED_INFORMATION`. The Microsoft page of that function documents `InheritedFromUniqueProcessId` as the parent pid, but it names no access right and calls the function internal. The code already works so for the Blocked Start; task 1.2 checks it for `msedgewebview2.exe`. The parent pid is the creator that Windows recorded. A process can name another parent with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` if it has `PROCESS_CREATE_PROCESS` on that parent, which the child has on its own `explorer.exe`. So a script can start a trusted WebView2 with `explorer.exe` as its creator; D13 accepts this.

Then it does with each counted process what `POST /api/agent/activity` does on main: skip a locked session, take the day from `ControlTime.Current.Today` (D14), `CategoryUsageRepository.CollectMinutes` and the whole minutes through `UsageLedger` (Pending Usage, not for System and not for a suspended exe), `AppUsageRepository.AddSeconds` with the file name and the title through `StorageHealth.TryWrite`, and `_liveActivities`. The user is the user of the session of the probe.

What this gives:
- A game that the child put into a System window with `SetParent` counts as a child entry, also if the focus stays on the host (B3).
- A System window that the child put into a game does not hide the game, because the game is `fg`.
- A Study window that the child put into a game does not hide the game either: both Games and Study count, which fails closed.
- A game window with `WS_EX_NOACTIVATE` counts while the cursor is over it, so a mouse-driven game counts (B3).
- A game inside a System window with `WS_EX_NOACTIVATE` counts while the cursor is over it (B5).
- A WebView2 control in a Study app counts as Study only, also as a popup in front (S16). A WebView2 flyout of `explorer.exe` (Windows 10 "News and interests") counts nothing and cannot lock the child (B4). A WebView2 control of a Games app that a script moved into Notepad counts in Games, and the app becomes a suspend candidate (S16).
- A game that the child copies as `msedgewebview2.exe` to a folder that it can write counts as itself, by its App Rule. With no rule for its folder, that is Unknown (S17: a file rule wins over a folder rule in `CategoryResolver`, and no default rule covers the copy). The rule of a program that is never suspended (below) locks the session if Unknown is exhausted (B4).
- A Store app gives `fg` = `ApplicationFrameHost.exe` (System) and the app as a child and usually as `focus`, so only the app counts.

**Why a `cursor` entry counts only with `WS_EX_NOACTIVATE` (B3).** The window under the cursor is often not the window that the child uses: the cursor rests on a background window while the child types or reads in the Foreground Window. To count each such window would charge the wrong category often. A `WS_EX_NOACTIVATE` window does not become the Foreground Window when the child clicks it. So a window with this style under the cursor is a strong sign of use without activation, and normal programs rarely show such a window under a resting cursor. Each other `cursor` exe is only a suspend candidate. False-count risk: an on-screen keyboard, a toast or an overlay of a non-System program with this style under the cursor counts in its category, and since B5 also each foreign process inside such a window. Task 1.2 logs each `cursor` entry and chain in normal use and is a gate.

**N25 is not adopted.** Re-review 3 suggested that a `cursor` entry without `noActivate` becomes a suspend candidate only after two samples in a row. That would delay the suspend candidate of a game that a script hides from the other roles, and a pass of the cursor over a background program of an exhausted category only suspends it, which the hard rule allows.

**A program that is never suspended still has a limit (S1, N16).** The rule is generic: each counted exe that `SuspensionPlanner` never suspends and that is not in System. Today these are the Session Agent, each exe with the file name `msedgewebview2.exe` (trusted or not, because `ProtectedPrograms` tests the file name), an exe below the install folder, and an exe below the Windows folder after the parent deleted the default System rule. If the category of such an exe is exhausted and the exe is a counted process for more than 60 seconds within 10 minutes of unlocked time, the service applies the fallback of a process that cannot be suspended: the Enforced Workstation Lock and one alert. This lock is a probe lock and follows the shadow mode (D12). A trusted WebView2 counts as its creator (rule 3), so it falls under this rule only if its creator is never suspended. Time in sleep or hibernation does not count in the 10 minutes (S20). A prompt of the parent needs no part of the 60 seconds, because the agent counts nothing during an active prompt (S10). Time that the Agent Window Budget exempts does not count toward the 60 seconds either, so the scenarios "Game drawn in the agent window" and "Agent window moved into Notepad" lock within 2 minutes after the budget is used up.

**The widget does not take the activation (B6).** Re-review 4 showed that `WidgetWindow` was a normal activating WPF window: a click on a button or a `DragMove` made the agent the Foreground Window until the child clicked somewhere else. With Unknown exhausted, a child who dragged the widget aside and then watched a video in a background window for a minute was locked. So the widget must never become the Foreground Window by a click or a drag:
- `ShowActivated="False"` in the XAML (the property "has no effect" after `Show`), and `WS_EX_NOACTIVATE` on its HWND in `SourceInitialized` (`GetWindowLongPtrW`/`SetWindowLongPtrW(GWL_EXSTYLE)`). Such a window "does not become the foreground window when the user clicks it".
- An `HwndSource` hook returns `MA_NOACTIVATE` for `WM_MOUSEACTIVATE`, which "does not activate the window, and does not discard the mouse message". So the buttons still get the click.
- The window and each of its buttons are `Focusable="False"`. WPF moves the keyboard focus into a focusable control at a click, and `SetFocus` also activates the window. The widget takes no keyboard input.
- The move: the docs do not say whether `DragMove` (the system move loop) activates a `WS_EX_NOACTIVATE` window, and `SetCapture` gives a background window mouse messages only "within the visible portion of the window". So the spec requires the outcome, and task 1.2 picks the means in this order: first `DragMove`; if that activates the widget, a move that polls `GetCursorPos` and the left button state and calls `SetWindowPos(SWP_NOACTIVATE)` until the button is up.
- Only if both activate the widget, the last fallback has two parts. First, after the mouse-up the widget gives the foreground back to the window that was in front before the click (agent code; injected code that skips it only keeps the agent `fg`, which fails closed). Second, a short exemption that uses probe facts and service state only, never agent data: the agent as `fg` adds nothing to the 60 seconds for at most 15 seconds after a sample with the agent in `cursor`, and for at most 60 seconds per 10 minutes. The exemption is short and bounded, because a game drawn in the agent window gets the same time; it covers the click itself, and the give-back covers the time after it. Its time counts against the Agent Window Budget below (one budget for all agent windows).

Injected code that removes the style makes the agent `fg` again, so the rule above still bounds a game drawn in the agent window (S1). Accepted cost (B6): the full-screen settings dialog (`FullscreenSettingsWindow`, opened with `ShowDialog`) and the tray menu of the agent take the activation while they are open. A child who leaves the dialog in front for more than 60 seconds while Unknown is exhausted is locked. An exemption that depends on the state of the agent would make a limit depend on agent data, so there is none. Task 1.2 records `fg` for each of these windows.

**Prompts of the parent (S10).** `PromptDialogWindow` is `Topmost` and calls `Activate()`, so it becomes the Foreground Window. Unknown has a default limit, so an exhausted Unknown is a normal state, and an urgent prompt that stays in front for more than 60 seconds would lock the session and use up Unknown time. So while the service has an active prompt for the user of the session, the agent counts nothing and adds nothing to the 60 seconds. This depends on service state (the parent sent the prompt), not on agent data. The service expires a prompt after 5 minutes (`SessionPromptRepository`), so the exemption is bounded and the parent starts each one. A capture request gives no exemption: a capture shows no agent window, and the watch mode lasts 10 minutes, which would give the child a free window.

**The Agent Window Budget (#54, D8 of `show-request-page-in-agent-window`).** *Decided by the orchestrator under the user's delegation (2026-11-27).* The Request Window of #54 is a WebView2 window of the agent. It takes the activation and the keyboard, so the non-activation of the widget does not cover it, and its trusted `msedgewebview2.exe` counts as its creator, the agent (rule 3), in Unknown (rule 5). A child asks for more time exactly when Unknown runs short, so the rule of a program that is never suspended would lock it after about one minute of typing. So the pure class `AgentWindowBudget` (Domain, from #54) exempts the agent as a counted process, in any role and also as the creator of a trusted WebView2, for at most 300 seconds in any 60 minutes of unlocked time. Its input is the probe samples and the lock state only, never agent data. Exempt time adds no Category Usage for the agent and does not count toward the 60 seconds of the rule of a program that is never suspended. It removes only the entry of the agent: another counted process of the same sample in the same category still adds the interval. It does not change the Allowance Time, Continuous Use, a Break or the Schedule Window. The probe cannot tell the agent windows apart, so the budget covers each agent window, and the widget exemption above (if the fallback needs it) counts against it. The prompt exemption (S10) stays separate. So a game that injected code draws in the agent window gets the budget plus the 60 seconds before the lock. The requirements "Agent Window Budget" and "The Agent Window Budget exempts only the Session Agent" move from `request-window` into `category-limits` with this change.

**Fixed Version and per-user WebView2 (B4 trade-off).** An app can ship its own WebView2 runtime (Fixed Version), or a user without admin rights can get a per-user runtime below `%LOCALAPPDATA%`. Such a `msedgewebview2.exe` is not trusted. In a Study app with the focus in the WebView2 control, it counts by its own App Rule. If no rule covers its folder, it counts in Unknown, and an exhausted Unknown then locks after 60 seconds, because `ProtectedPrograms` never suspends the file name. The parent fixes this with an App Rule for the folder of the app. Task 1.2 lists each `msedgewebview2.exe` path in normal use. GitHub issue #48 changes `ProtectedPrograms` and `SuspensionPlanner` to the same path test, so that an untrusted copy is suspended instead of the lock; that changes the specs `blocked-programs` and `category-limits` outside this change. #48 is a prerequisite of the release (S22, D12, task 7.4): its change comes after `/opsx:archive` of this change and modifies the archived scenario "Game renamed as WebView2" and the list of programs that are never suspended above.

The service also starts the agent without the variables `DOTNET_*`, `COMPlus_*`, `CORECLR_*` and `WEBVIEW2_*` in its environment (S1; `WEBVIEW2_*` from #54 Review 1 N10: the child could set `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` with a debug port for the Request Window). This removes the injection that needs no code; the child can still inject with a tool, which the counting rule above covers for the agent. Code that the child injects into another program of its own that is in System is a residual risk without a bound (S11, D13).

**`ForegroundHistory` cap (S5, N14).** `ForegroundHistory` is a set of distinct exe paths per user and day, not a list of samples. The cap rises from 1000 to 60,000 paths. A child would need 60,000 different exe files, each seen in a sample, to fill it; at one sample about every 5 seconds that takes more than 80 hours. The cap stays as a bound on memory. If it is reached anyway, `Record` returns false, and the service applies the Enforced Workstation Lock and sends one alert (fail closed), because an exe that is not in the set is not a suspend candidate. This lock is a probe lock and follows the shadow mode (D12).

### D6. When the probe gives no samples (fault)
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for N10, for S15, for S20, N26, and for the end classification of the review decisions).*

A pure class `ProbeOutageMonitor` (Domain) keeps the time of the last sample per session. If an unlocked, connected session of a Restricted User has no sample for 5 minutes, measured without sleep and hibernation (S20, D2), the service writes the event `PROBE_OUTAGE` (new value of the existing `EventType` enum) and sends the parent a Telegram alert. It sends one alert per outage, and at most one per Restricted User and hour (N10), so a repeated fault stays visible. During the gap no category time counts beyond the gap rule of D5. The watchdog of D2 ends a silent probe after 30 seconds, and the service starts a new probe after the delays of D2 after each end that it did not ask for (S15). The session Allowance Time counts as before, because it does not depend on samples.

**Unexpected ends count (S15).** `ProbeOutageMonitor` also counts the unexpected ends of D2 (crashes, other exits, watchdog kills) per Restricted User:
- The service writes the event `PROBE_RESTART` (new value of `EventType`) for each one.
- From the 3rd unexpected end within 10 minutes of unlocked, connected time, each unexpected end is one budget item of D6a (never the strike, N26). The service decides the class of an end only at the end of the end wait of D2 (90 seconds), and only then writes the event and adds the item. A session-end end and a benign end (an end in the resume window after a resume, S20) do not count. A probe that the child can crash one minute after each start ends about every 61 to 66 seconds with the delays of D2 (1, 2, then 5 seconds, plus the start of the probe). The ends come at about 0, 1.0, 2.1, 3.2, 4.3, 5.4, 6.5 and 7.6 minutes. The 8th end gives the 6th budget item 90 seconds later, at about 9.1 minutes, so the session is locked then; the spec allows 10 minutes. Its time counts in between (no reset of the gap, D5; a gap over a probe end is no gap item). One crash a day from a real bug does nothing.
- At the 3rd unexpected end within one hour, the service sends one Telegram alert, at most one per Restricted User and hour. This alert also comes at the end of the end wait.

An outage that the child cannot cause is a fault, not a child action: the child cannot end, suspend or open the probe (D1, D2), and a CPU load of the child stalls the probe only for a gap that the gap rule of D5 handles (task 1.5 measured gaps of up to 34.2 seconds on VM 102). But the probe parses window data that the child controls. D3 drops a strange line without an end of the probe, but a crash or a hang of the probe from such data is possible until tests prove otherwise. So the unexpected ends feed the budget, and the shadow mode (D12) covers the risk that a real probe bug locks the child.

Rejected alternatives:
- **Agent samples as a fallback.** The child controls them. This is the hole of #6.
- **A conservative count from the process list** (each category with a running process that was in front today counts during the gap). It punishes the child for a fault of the service, and the child cannot stop a SYSTEM process.
- **The Enforced Workstation Lock during a gap**, as in Data Folder Lockdown. Too strong for a fault of a helper. The alert lets the parent act.

### D6a. Blind samples lock the session (B1)
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for B1 and B2, for B3, S9, N11, N13, N18, N20, and for S14, S15, N23, N24, for S20, and for the gap rule and the lock state of the spike).*

**One definition (N24).** The budget below takes two kinds of items. The spec "Blind samples" and the glossary term Blind Sample use the same list.
- **A blind sample** (budget and strike): a sample that shows that a window or desktop is there, but that the service cannot attribute to an exe. These are:
  - `{ "blind": "desktop" }`: the input desktop cannot be opened or set;
  - `{ "blind": "window" }`: a window is in front, but it gives no thread;
  - `{ "blind": "children" }`: more than 8 other processes have visible windows below `fg`, or the walk passed 4096 windows (B3);
  - a sample with an Unreadable entry (D3b).
- **A budget item** (budget only, never the strike):
  - a sample with an Ended entry in a role that would count time (D3b, S9, S14);
  - a gap of more than 12 seconds whose two samples are not the same under the sameness test of D5, and each gap of more than 60 seconds (the gap rule of D5, spike 1.5), except a gap over a probe end;
  - from the 3rd unexpected end of the probe within 10 minutes, each further unexpected end (D6, S15). A session-end end and a benign end of D2 are no item;
  - a sample that takes more than 12 seconds (`dur`, D3), for the gap that ends at it (D5).

The child can cause each blind sample: a desktop with a security descriptor that denies SYSTEM, a DACL on its game process or thread, decoy child windows. So blind samples must fail closed. A budget item can also come from an honest window close or a real probe bug, so it never triggers the strike.

**The session state at the sample (N23).** For each blind sample and each budget item, the service queries the connect state of the session at once with `WTSQuerySessionInformationW(WTSConnectState)`, and ignores the item if the state is not `WTSActive` or `SessionTracker` has the session as locked (the lock notification, D4). It does not rely on the order of the WTS notifications. So a sample from the disconnect or reconnect of a fast user switch, or from the disconnect of the lock itself, never hits the strike. For the budget item of an unexpected end of the probe, the service queries the state at the end itself and keeps it, because the item comes only at the end of the end wait (D2).

The first draft locked after 30 seconds of only blind samples, and one readable sample reset the timer. The review showed the attack: 25 seconds on the hidden desktop, 5 seconds back on the default desktop, again and again, and the timer never runs out. So the rule is a rolling budget (`BlindSampleBudget`, a pure class in Domain, part of `ProbeOutageMonitor`):
- The service keeps the times of the blind samples and the budget items of each Restricted User for the last 10 minutes of unlocked, connected time. Locked, disconnected and signed-out time, and time in sleep or hibernation (S20), do not count in the 10 minutes, as for Continuous Use. The service ignores items from a session that is locked or not connected (N23). Readable samples do not remove an item.
- At the 6th item (blind samples and budget items together) within these 10 minutes, the service applies the Enforced Workstation Lock through `SessionLocker` (D14), writes the event `PROBE_BLIND` (new value of `EventType`; the first revisions named it `PROBE_DESKTOP_DENIED`, but it also covers unreadable processes, N18) and sends one Telegram alert per Restricted User and day. 6 samples are about 30 seconds of hidden time (D4).
- After the first such lock of a Restricted User on a day, each blind sample on that day locks at once (the strike). A child who tried once does not get a new budget after each unlock. A budget item does not trigger the strike.
- The lock at the 6th item and the strike are probe locks and follow the shadow mode (D12): while the probe locks are off, the service writes the event and the alert of a "would lock", and the budget and the strike advance as if it had locked.
- The budget and the strike are in memory. A service restart clears them; only an administrator can restart the service.

With the random sample times of D4, a child who hides for a share of the time produces about that share of blind samples. The alternation of 25 s and 5 s gives about 5 blind samples per 30 seconds and a lock within about 40 seconds. A direct switch to a hidden desktop needs 6 blind samples; with 0.2 s plus a random time with a mean of 4.8 s, at most 10 s, they take about 27 ± 7 seconds, so the spec allows 60 seconds (N13). A child who sees each sample can still show a game for about 0.2 seconds after each one without a blind sample (N11). That is about 4 % of the time, in pieces too short for a game.

This follows the fallback when a process cannot be suspended (`add-app-categories` D6). No program is closed.

**The desktop after the unlock (N20).** The Enforced Workstation Lock disconnects the session (`WTSDisconnectSession`). Which desktop Windows shows when the child signs in again is not measured yet. If Windows shows the hostile desktop of the child again, the strike locks again at the next blind sample, a lock loop for the rest of the day. The child can leave the loop with Ctrl+Alt+Del and Task Manager (Task Manager opens on the default desktop), and the parent has the alert. Task 1.5 recorded on VM 102 that Windows shows the default desktop after the sign-in, so the gate holds. The named fallback stays for the case that the child's PC differs: after each unlock, the service ignores blind samples until the first readable sample, for at most 15 seconds, so that the child can switch back. Each such pause of the blind samples needs a full sign-in of the child, so it gives little play.

Rejected alternatives:
- **A timer that a readable sample resets** (the first draft). The alternation attack defeats it.
- **No count while the desktop is not readable.** This is the hole of #6 again, through a different door.
- **A conservative count from the process list.** A game that the child starts on the hidden desktop was never seen in front, so it is not a candidate (D3b of `add-app-categories`), and the count misses it.
- **Give the probe a privilege to bypass the desktop DACL** (`SeTakeOwnershipPrivilege` and a new DACL on the desktop of the child). This changes an object of the child and gives the probe a strong privilege. The lock is simpler and sure.

### D7. The Agent Channel: a pipe that the service owns, with the client end inherited by the agent
*Decided by the orchestrator under the user's delegation (2026-11-26; revised 2026-11-27 for S7, N2, N3, N9, and for S12).*

For each agent start, the service (`AgentChannelHost`, new):
1. Creates a named pipe `\\.\pipe\ParentalControl.Agent.<32 random hex digits>` with `CreateNamedPipeW(PIPE_ACCESS_DUPLEX | FILE_FLAG_FIRST_PIPE_INSTANCE | FILE_FLAG_OVERLAPPED, PIPE_TYPE_BYTE | PIPE_REJECT_REMOTE_CLIENTS, maxInstances: 1)` and a security descriptor that gives access to SYSTEM only. The child cannot open the pipe by name and cannot create an instance.
2. Opens the client end itself with `CreateFileW(GENERIC_READ | GENERIC_WRITE, FILE_FLAG_OVERLAPPED | SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION)`, not inheritable. `ConnectNamedPipe` completes at once. `FILE_FLAG_OVERLAPPED` is required (S12): the agent uses the handle for asynchronous I/O, and `ThreadPoolBoundHandle.BindHandle` throws `ArgumentException` for a handle that was not opened for overlapped I/O. The flag belongs to the file object, so the inherited duplicate has it too.
3. Starts the agent with the user token as today (`WTSQueryUserToken`, `DuplicateTokenEx`, `CreateEnvironmentBlock` with the user token, minus `DOTNET_*`, `COMPlus_*`, `CORECLR_*` and `WEBVIEW2_*` (D5)), but with `bInheritHandles: true`, `EXTENDED_STARTUPINFO_PRESENT` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` with an inheritable duplicate of the client handle, under `ProcessLaunchLock` (D2, N6). The command line is `"ParentalControl.Agent.exe" --channel <handle value>`.
4. Closes its copies of the client handle and keeps the launch record: the server end, the agent process handle, the pid, the start time, the session ID and the user SID. The user SID comes from `GetTokenInformation(TokenUser)` of the token that started the agent (N9), not from a user name.

The agent wraps the handle in a `SafePipeHandle` and a `NamedPipeClientStream(PipeDirection.InOut, isAsync: true, handle)`. The overload with `isConnected` is obsolete in .NET 10 (`SYSLIB0063`), and its `isConnected` has no effect. It checks `GetFileType == FILE_TYPE_PIPE` and `GetNamedPipeServerSessionId == 0`, else it exits. This check is only a guard for the user interface (N2): a fake server of the child can only feed false texts to the agent of the child, which the child controls anyway. No security decision depends on it. If the channel breaks, the agent exits. A new service run starts a new agent (D9).

Framing: each message is a 4-byte little-endian length and a UTF-8 JSON object with `type` and `id`. The agent sends requests; the service answers each one. Types: `status`, `promptAnswer` (`promptId`, `response`, `reason`, `turnaroundSeconds`), `capture` (`trigger`, `width`, `height`, then the JPEG bytes as a second frame), `sessionEnding` (`reason`). No message has a user or a session field; the service ignores such fields (spec "The service takes the identity of an agent message from the launch"). A pure class `AgentChannelCodec` (Domain) does the framing and the limits.

**Limits against a flood or a stall (S7).** The child controls the client end, so the service treats the channel as hostile input:
- The service reads the 4-byte length first and checks it before it allocates: at most 64 KB for a JSON frame, at most `CaptureQuota.MaxBytesPerCapture` for a JPEG frame that follows a `capture` frame. A larger length closes the channel.
- All reads and writes are asynchronous (overlapped). A frame must arrive within 10 seconds after its length; a write of the service must complete within 5 seconds. Else the service closes the channel. A slow or silent agent never blocks a thread of the service or another channel.
- Each channel has a rate limit: at most 5 messages per second and 30 per 10 seconds; a capture counts against `CaptureQuota` as today. Over the limit the service drops the message, and after 10 dropped messages it closes the channel.
- Each channel object holds its own launch record; no handler reads a shared "current user". After a close, the agent exits and the service starts a new one within 60 seconds (D9). The child can only stop its own agent with a flood.

**What this proves, and what it does not.** It proves that a message comes through the handle that the service gave to the agent process that it started, in that session, as that user. It does not prove that the agent code sent it. The child owns the agent process: it can load a DLL into it with `SetWindowsHookEx`, start a thread in it with `CreateRemoteThread`, attach a debugger, or copy the channel handle into another process with `DuplicateHandle`. So the channel gives the identity of the session and the user, not trust in the data. D10 makes sure that no limit needs more.

Rejected alternatives:
- **A named pipe with an ACE for the child's SID, and a check of the client** (`GetNamedPipeClientProcessId`, then the image path below the install folder, `ProcessIdToSessionId`, and pid + start time equal to the launch record). It proves the same as D7 and no more: the child can still inject or duplicate the handle. It needs more parts: an ACE that must not include `FILE_CREATE_PIPE_INSTANCE` (else the child creates a server instance and takes the agent's connection), a pid check with a race against pid reuse, and a reconnect logic. It stays the fallback if the VM check of task 1.1 shows that the handle inheritance across sessions does not work. In the fallback, the service takes the user SID and the session from the client token (`ImpersonateNamedPipeClient`, `OpenThreadToken`, `TokenUser`, `TokenSessionId`), not only from the pid (N3).
- **A secret token** on the command line, in a file or in the registry. The child reads the command line and the memory of its own agent.
- **HTTP with the owner check of the TCP connection** (`TcpConnectionOwner`, as for the admin login). The same proof as the named pipe check, plus the port 5050 that another program can hold.
- **The agent at High integrity level** (a user token with a raised label through `SetTokenInformation(TokenIntegrityLevel)`), so that the child cannot inject into it or end it. The programs that the agent starts (the request page in the browser) inherit the High level, UIPI blocks drag and drop and some input from the child's programs, and the effect on the tray and the audio APIs is not known. The probe gives the facts, so the agent does not need this protection.
- **A DACL on the agent process** that denies `PROCESS_VM_WRITE` and `PROCESS_CREATE_THREAD` to the child. `SetWindowsHookEx` loads a DLL into each GUI process at the same integrity level on the desktop and does not check the DACL of the process.

### D8. What the service does with agent messages
*Decided by the orchestrator under the user's delegation (2026-11-26).*

- `status`: the same answer as `GET /api/agent/status` today, for the user of the launch record. The capture request and the active prompt are those of that user. A non-restricted user (an Administrator) gets the prompts and `isRestricted: false`, as today.
- `promptAnswer`: accepted only for an active prompt whose user SID is the SID of the launch record. Else the answer is refused and nothing changes.
- `capture`: the quota and the file logic of `POST /api/agent/capture`, with the user of the launch record. The column `admin_ip` of `screen_captures` gets NULL for an agent capture. No new column.
- `sessionEnding`: as the route on main does, first `SessionLocker.OnSessionEnding(sessionId of the launch record, ..., trusted: false, ...)` (the Lock Deferral, #51), then `CategoryEnforcer.ResumeSessionForEnd(sessionId of the launch record, user, trusted: false, ...)` (the hold, or else the Session End Guard, #49). The answer does not say whether the deferral was granted. The limits of the Lock Deferral, the Session End Hold and the Session End Guard stay: the child can make its agent send this message, and the child can also send `WM_QUERYENDSESSION` to the hidden window of the agent.
- The mute list: the agent takes the pids from `suspendedApps` of the status poll (every 5 s). `ActivityTracker` and its activity timer go away.

### D9. One agent per session, owned by the service (#32)
*Decided by the orchestrator under the user's delegation (2026-11-26).*

`SessionManager.LaunchProcessInSession` returns the process handle, the pid and the start time instead of a bool. A pure class `AgentLaunchRegistry` (Domain) keeps one launch record per session and decides: start an agent if the session has no record or if the process of its record ended; else do nothing. `EnsureAgentRunning` uses it and no longer searches processes by image path. So a process of the child with the agent name or the agent exe cannot make the service think that the agent runs. `IsAgentRunning` (the prompt route of the admin page) also reads the registry.

The agent removes the named mutex. An agent without `--channel`, with a handle that is not a pipe, or with a server outside session 0 exits at once. The installer removes the `Run` value `ParentalControlAgent` (also from an old install), so the service is the only process that starts the agent. An agent that the child ends is started again at the next tick (at most 60 s), as today.

Rejected alternatives:
- **A mutex that the service creates with a DACL for SYSTEM only**, and an agent that checks the owner of the mutex. The child can create the name first while the service is not running (for example during an update), and the check of the owner adds code. The channel already gives one agent per session.
- **Keep the mutex and add a check.** Each named object in a namespace that the child can write can be taken first.

### D10. No limit reads agent data
*Decided by the orchestrator under the user's delegation (2026-11-26).*

After this change the Session Agent sends only: status polls, prompt answers, screen captures and session-end requests. The service uses them only to show texts, to mute and minimize windows, to record a prompt answer, to store a capture and to ask for a Session End Hold under its rate limit. Category Usage, `ForegroundHistory`, App Usage, the Allowance Time, Continuous Use, suspensions and resumes do not read agent data (spec "No limit depends on data of the Session Agent").

### D11. Migration: the HTTP agent routes go at once
*Decided by the orchestrator under the user's delegation (2026-11-26).*

The five routes below `/api/agent/` go in the same release as the channel. The web server answers 404 for them.
- The installer ships the agent and the service together. It closes the running agent (`CloseApplications=force` and `taskkill`), and the new service starts a new agent with a channel.
- An old agent that survives the update gets 404 and shows a stale widget until the next sign-in. No limit depends on it.
- To keep the routes for one version keeps #6 open for that whole version. Rejected.
- `/`, `/request`, `/api/request` and the web admin are not agent routes and stay on HTTP. The port-squat warning (`ReportSquatAsync`) no longer names `/api/agent/activity`.

### D12. Shadow mode: the probe locks start off (S19)
*Decided by the orchestrator under the user's delegation (2026-11-27, Re-review 3; revised 2026-11-27 for S22).*

Re-review 3 noted that one hour on a VM cannot show that false blind samples and false locks are absent, and the strike makes each false blind sample expensive. So the first release runs the locks of the probe in a shadow mode. The service logs and reports each lock that it would apply, and applies these locks only after the parent switches them on.

**The probe locks** are the locks that this change adds:
- the lock at the 6th item of the budget, and the strike (D6a);
- the lock of a program that is never suspended after 60 seconds in an exhausted category (D5);
- the lock of a full `ForegroundHistory` (D5).

Each other lock of the product (the Allowance Time, the Schedule Window, the fallback of a process that cannot be suspended outside this change, Data Folder Lockdown) is not a probe lock and works as before.

**The setting.** The new key `probe_locks_enforced` in `SettingsRepository` ("1" on, else off) is off while the key does not exist, so it is off on a new install and after the update to this release. A later update keeps the stored value. The parent changes it on the settings page of the web admin, which requires an Admin Session. Next to the switch, the page shows the number of "would lock" events of the last 7 days. No new table and no new column. At the switch to on, the service clears the budget and the strike of each Restricted User, so the switch itself never locks at once.

**While the probe locks are off:**
- At each decision to apply a probe lock, the service skips the lock (`SessionLocker`). It writes the event `PROBE_WOULD_LOCK` (new value of `EventType`) with the reason (blind samples, a program that is never suspended with its exe path, or a full set). It sends one Telegram alert per Restricted User, day and reason, and for a program that is never suspended one alert per exe and day that names the exe path (S22). So the parent sees each such exe on the day it first plays and can add an App Rule or a block at once. The strike can repeat the decision at each sample, so the service writes at most one `PROBE_WOULD_LOCK` event per Restricted User and minute, with the number of decisions in that minute.
- The budget and the strike advance as if it had locked, so the log shows what the probe locks would have done.
- The counting from the probe, the suspensions, the outage alert and the restart alert work as specified.

**Why the counting cannot be shadowed.** The orchestrator asked for a log of "would count" decisions too. D11 removes the HTTP agent routes in the same release, so the probe samples are the only source of Category Usage. If the counting were only logged, no limit would work during the shadow time. If the agent samples counted instead, issue #6 would be open again, which breaks the rule of `CLAUDE.md`. So the counting is live from the first day. For the review of false counts, the service logs each sample in which an entry other than `fg` (a focus, child or `cursor` entry, or a WebView2 creator) adds a category that `fg` does not add, at most one line per exe, role and hour. The suspensions are live too: they only suspend, as the hard rule allows.

**The rollout.** Before the release tag, the release gates of D15 (task 9.1) run on the child's PC. The release runs on the child's PC in shadow mode for at least 7 days of normal use. The parent switches the probe locks on only when task 9.1 passed and the log shows no false "would lock". The code does not enforce the 7 days.

**The cost.** While the probe locks are off, a hidden desktop, a DACL that the service cannot pass, a program that is never suspended, and a crash loop of the probe give the child free time, and the parent gets the alerts above. This is accepted for the shadow time.

One case of this cost needs no script (S22): a game that the child copies as `msedgewebview2.exe` into a folder that it can write (for example Downloads). It counts in Unknown (D5), `ProtectedPrograms` never suspends the file name, and its only limit is the lock of a program that is never suspended, a probe lock. So until #48 lands, shadow mode gives it unlimited play with Explorer actions only. Two measures bound it: the alert per exe above names the copy on its first day, and GitHub issue #48 (suspend an untrusted `msedgewebview2.exe` by its path) is a prerequisite of the release (task 7.4), so the released product suspends the copy when Unknown is exhausted, also in shadow mode.

Rejected alternatives:
- **No shadow mode.** The strike turns one false blind sample into a lock, and the VM cannot show that such samples are absent on the child's PC.
- **Agent counting during the shadow time.** It opens issue #6 again.
- **An automatic switch to on after 7 days.** No person checks the log before the locks apply.

### D13. The end of the design chase for script bypasses
*Decided by the orchestrator under the user's delegation (2026-11-27, Re-review 3).*

Three review rounds each found a new way to hide a game from the sampled windows with a script that uses the window API (B3 with `SetParent` and `WS_EX_NOACTIVATE`, then B5 with both together, then the WebView2 move of S16). Each fix adds rules and false-lock risk, and the window API has more such tricks. So after this round the design stops the chase. It fixes B5 and S16 because the fixes are cheap and add no new blind sample. Each remaining class that needs a script or code is listed under "Accepted script and code bypasses" in Risks as accepted and without a bound, with the mitigation of the parent. A later finding in one of these classes goes into that list, not into a new rule, unless its fix is cheap and adds no false-lock risk. A finding that needs no script (a normal program or a setting of Windows) still gets a fix.

*Added by the orchestrator under the user's delegation (2026-11-27, review decisions):* the stall of the probe under a CPU load of the child is class 6 of that list. It needs no script (the child can set its game to High priority in Task Manager), so it gets a fix: the gap rule, the long-sample rule and the `PROBE_GAP` event and alert of D5. The rest of the case has no cheap fix and is accepted.

### D14. Fit with main after #40, #49 and #51
*Decided by the orchestrator under the user's delegation (2026-11-27, fifth revision).*

Main changed three things that the probe rules touch. The change adopts each one; it adds no new mechanism.
- **Lock Deferral (#51, capability `session-lock`).** Each probe lock (the budget lock and the strike of D6a, the lock of a program that is never suspended, the full-set lock of D5) goes through `SessionLocker`, never through `SessionManager.LockSession` directly. During a Lock Deferral the lock is owed. At the end of the deferral the service checks again and locks within 10 seconds if the lock is still due: the strike is set or the 10-minute window still holds 6 items; the exe of a program that is never suspended still counts while its category is exhausted; the set is still full. An owed probe lock follows the shadow mode like each other probe lock. A deferral does not stop the probe or the counting.
- **Storage rules (#40, capability `storage-failure`).** A probe lock calls the lock before any write of its path. A failed write of a `PROBE_*` event, a log line or an alert does not stop it. Category Usage from the probe goes through `UsageLedger`, so a failed write keeps it as Pending Usage. The scenario "Agent sample during a failure" keeps its name (the CLI refuses a renamed scenario in a MODIFIED block), but it now describes a probe sample.
- **Control clock (#40, capability `control-clock`).** Each day of this change is the day of the Control Time Zone (`ControlTime.Current.Today`): the strike "of the day", each alert "per day", the set of `ForegroundHistory`, the Category Usage day, and the "last 7 days" of `PROBE_WOULD_LOCK` events on the settings page. Each interval stays monotonic (`GetTickCount64`, `QueryUnbiasedInterruptTime`, D2), so a time zone change neither adds nor removes time.
- **Session End Guard (#49).** A probe suspension is a normal suspension: the hold and the guard delay it as on main. The lock of a program that is never suspended is a lock, not a suspension, so the guard does not delay it; the Lock Deferral does. The `sessionEnding` message of the channel starts the deferral and the hold or the guard as the route on main does (D8). The scenarios of `session-lock` and `category-limits` that named `curl` now make the Session Agent send the request, because the route answers 404 after D11.

### D15. Spike gates that need the child's PC become release gates
*Decided by the orchestrator under the user's delegation (2026-11-27, sixth revision).*

The VM spike (task group 1) ran on VM 102 on 2026-11-27. Four checks cannot finish there, because they need a person, real programs, other hardware or the OS of the child's PC:
- task 1.2: the common programs (Word, Edge and Chrome in use, a game launcher, the on-screen keyboard, a toast, "News and interests", the real widget, the tray menu) and one hour of normal use;
- task 1.5: the repeat of the CPU-load line, which failed on VM 102 with a cause that is not confirmed;
- task 1.6: sleep and resume, because VM 102 has only hibernation;
- task 1.7: the Windows version, the edition and Modern Standby of the child's PC.

These checks do not block the implementation (groups 2 to 8). They are release gates: before the release tag of this change, which turns on the probe counting, a log-only spike build runs these checks on the child's PC, and the results go into `tasks.md` (task 9.1). The log-only build is `ProbeSpike` of `scripts/vm/tools` only, updated to the rules of this revision (the end classification of D2, the ghost rule of D4, the gap rule of D5). It never locks, suspends or closes a program.

*Revised by the orchestrator under the user's delegation (2026-11-27, review decisions):*
- **Only `ProbeSpike` goes on the child's PC.** `SpikeKid`, `SpikeHook`, `SpikeWinHook`, `TestGame` and each other attack or test tool stay on the VM. Reason: the child's PC is a real target, and each of these tools is a ready attack for the child.
- **The `ProbeSpike` build for the child's PC has no test switch.** It is published without `-p:VmTest=true`, so `probeArgs`, the channel test and the crash and hang switches of the probe do not exist in it (the compile symbol `VM_TEST`). The service creates its folder `C:\ProgramData\probespike` with an ACL for SYSTEM and Administrators only (owner SYSTEM, protected, no inheritance) before it reads or writes anything. It refuses to start if that folder exists with another owner or a weaker ACL, or if another account can change its install folder or exe. It starts the probe only from its own install folder. Reason: the first spike service read the probe folder and its arguments from a file that a standard user could create, so the child could have made the SYSTEM service run its exe. A compile symbol was chosen over a check of the machine name, because a build without the switches cannot be turned on by a setting.
- **The CPU load on the child's PC comes from the child's own programs**: a real game of the child at High priority (Task Manager) and a second CPU-heavy program of the child at High priority. The attack form (one time-critical thread per core plus 4 in a High process) stays a VM test (`category-limits` scenario "CPU load of the child", task 4.6). Reason: no load tool of the spike goes on the child's PC. The test measures the honest case that the child can make without a tool.
- **The log-only build counts with the release code.** It references `ParentalControl.Domain` (`net10.0`) and uses `ForegroundSampleCounter`, `CountedProcesses` and `ProbeOutageMonitor` (tasks 2.1 to 2.3) and the rules of S20 (the unbiased time for the watchdog, the outage timer, the resume window and the backstop of D2). So its results match the release. Task 9.1 runs after tasks 2.1 to 2.3.
- **After the run, all spike files and the service go**: `sc stop ProbeSpike`, `sc delete ProbeSpike`, the install folder and `C:\ProgramData\probespike` (after the log is copied off), and a check that no `ProbeSpike.exe` process remains. Task 9.1 records each step. If the child's PC runs Windows 11, the checks of tasks 1.2 and 1.5 run there too.
- A failed check that changes the counting (a wrong category in a common case, a CPU-load undercount) blocks the release until `/opsx:update` or a fix and a new run pass.
- A failed check that only gives false items or false locks keeps the probe locks off (D12, `probe_locks_enforced`) until `/opsx:update` or a fix and a new run pass.
- In each case, the probe locks stay off until task 9.1 passes.

Rejected alternatives:
- **Keep the gates before group 4.** The implementation then waits for the child's PC, and the VM cannot answer these checks.
- **Release without these checks.** The counting is live from the first day (D12), so a false count on the child's PC would charge the child at once.

## Risks / Trade-offs

**What the child can still do after this change (residual risk):**
- **Fake its own screen captures.** With code in its agent, the child can upload any image as its capture. Captures are a monitoring help, not a limit. A later change can move the capture into the Session Probe.
- **Get about 80 seconds of play per 15 minutes** with a false session-end request (the hold plus 20 s), as today. The rate limit stays.
- **Get about 25 seconds of hidden play per 10 minutes** if it stays below the budget of D6a (5 blind samples); the 6th locks, and after that lock each blind sample of the day locks. And about 60 seconds per 10 minutes in a program that is never suspended after its category is exhausted (D5), and about 4 % of the time in pieces of 0.2 seconds after each sample (D4). Hidden play in pieces of a few seconds, with a desktop switch each time, is of little use for a game.
- **Use a script or code bypass from the list below (S11, D13). No bound,** except class 6 (a stall that the child times with its own CPU load: at most 60 seconds per gap in the category of the window at both ends, with an alert).
- **Get free time while the probe locks are off** (D12): a hidden desktop, a DACL that the service cannot pass, a program that is never suspended, or a crash loop of the probe give free time with the alerts of D12, until the parent switches the probe locks on. A game copied as `msedgewebview2.exe` is in this list only until #48 lands, which is a prerequisite of the release (S22).
- **Stop its own widget, warnings in the agent, mute and minimize.** This hurts only the child. The service warnings through `WTSSendMessage` and the suspensions do not depend on the agent.
- **Answer its own prompts with any answer.** The answer is the child's anyway.
- **Use a program that is not in a sample**: its window is not the Foreground Window, has no focus, is not a visible child of the Foreground Window, and is not a `WS_EX_NOACTIVATE` window under the cursor (B3). Examples: a video in a background window, a game with `WS_EX_NOACTIVATE` that the child plays with the keyboard, a gamepad or raw input (`RIDEV_INPUTSINK`) while the cursor rests on another window. Such a game is still a suspend candidate when the cursor passes over it. Or leave a game in front without use. Out of scope (idle and background use). No bound for the game case, but it needs a game that takes input without activation.
- **Copy or rename a game exe** so that a file-name rule of another category matches. Out of scope (stage 4: hash or signature rules).
- **Put a game into a folder below `C:\Windows` that a standard user can write** (S2). The exe counts as System and is never suspended. This is a pre-existing hole of the System rule, not of the probe; GitHub issue #45 handles it.
- **Resume a Suspended App with a tool again and again** (#24). Out of scope.

**Accepted script and code bypasses (D13).** Classes 1 to 5 below need a script (PowerShell `Add-Type`, AutoHotkey `DllCall`, a VBScript or HTA file) or code of the child. Each one can make a game count no time and stay out of the suspend candidates. This change accepts each class, and none of them has a bound. Class 6 needs no script and has a bound.
1. **Code injected into a System program.** The child loads code into its own `notepad.exe`, `mspaint.exe` or `explorer.exe` (`SetWindowsHookEx`, `CreateRemoteThread`) and draws a game in a System window.
2. **A Windows script host that shows a game.** A PowerShell script with a web control, an HTA file in `mshta.exe`, or a `wscript.exe` or `cscript.exe` script draws the game in a System window.
3. **A window of a game that no sampled role sees.** A script or code moves, restyles or covers windows so that the game is not `fg`, not the focus, not a visible child of `fg`, and not on the `noActivate` chain under the cursor. Examples:
   - a game that refuses activation in its window procedure (`MA_NOACTIVATE`) without the style `WS_EX_NOACTIVATE`;
   - a `WS_EX_NOACTIVATE` game played with the keyboard, a gamepad or raw input while the cursor rests elsewhere;
   - a chain under the cursor with more than 8 processes or 32 steps (D4 step 6);
   - a transparent or hit-test-transparent System window over the game, so that `WindowFromPoint` returns another window;
   - input that a script forwards from a System window to a hidden game (`PostMessage`, `SendInput`);
   - a picture of a hidden game in a System window (a DWM thumbnail, the magnifier API, a screen copy);
   - each variant of B5 that the spike finds and that a cheap fix without false-lock risk cannot close.
4. **A false creator of a trusted WebView2** (S16). A script starts `msedgewebview2.exe` from the WebView2 Runtime with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` and its own `explorer.exe` (System) as the parent, or makes its parent chain fail the start-time test, so that the WebView2 counts nothing.
5. **A WebView2 control in a System host.** A script puts the WebView2 control of a System program (for example "News and interests" of `explorer.exe`) or of its own script host on a game page. The creator is System, so nothing counts.
6. **A stall of the probe that the child makes and times** (review decision, D13). The child starts a CPU load (for example High priority of its game in Task Manager; no script is needed) while a Study window is in front, plays a game during the stall, and shows the Study window again before it stops the load. The gap then counts in Study. Unlike classes 1 to 5, this class has a bound: at most 60 seconds per gap (D5), and each gap writes `PROBE_GAP` with one alert per day.

Mitigation of the parent:
- For classes 2, 4 and 5 when the script host draws: a file App Rule that moves `powershell.exe`, `pwsh.exe`, `mshta.exe`, `wscript.exe` and `cscript.exe` out of System. Then the script host counts when it is in a sample, and because the Windows folder is never suspended, the rule of a program that is never suspended locks the session when that category is exhausted.
- For classes 1, 3 and 4 when the script or tool has no window in a sample: the App Rule does not help. Third-party script and injection tools (AutoHotkey, AutoIt, a DLL injector) are outside the Windows folder, so the parent can make them Blocked Programs; the service closes them at their start. A block of the Windows script hosts needs a Windows policy (AppLocker or Windows Defender Application Control on editions that have them), which is outside this product.
- The alerts (`PROBE_BLIND`, `PROBE_RESTART`, `PROBE_GAP`, `PROBE_WOULD_LOCK`) and the admin page (App Usage, live activity) show unusual use to the parent.
- Code signing, rules by hash or signature, and a block of the Windows script hosts are later changes.

**Other risks:**
- [A bug in the probe is SYSTEM code in the session of the child] → The probe has no window and no input from the child except the window handles, ids and strings that it reads, which it only copies. It opens no process. It has no privileges (D2), the environment of SYSTEM without runtime variables, a SYSTEM-only DACL on its process, thread and default objects, no diagnostics, and files that only administrators can change. Native AOT is a later option.
- [The service opens processes of the child with `SeDebugPrivilege`] → It asks only for `PROCESS_QUERY_LIMITED_INFORMATION` and `THREAD_QUERY_LIMITED_INFORMATION` for a sample, as `ListProcesses` does today; the suspension asks for `PROCESS_SUSPEND_RESUME` as today. The privilege changes which handles the service gets, not what it does with them.
- [Handle inheritance across sessions with `CreateProcessAsUserW` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` does not work as expected] → Task 1.1 checks it on the VM before any other work. If it fails, D7 uses the rejected named-pipe variant with the client check, and D3 uses a named pipe with a SYSTEM-only DACL.
- [A SYSTEM process in the session delays the end of the session or keeps the session alive] → The probe has no window, so it gets no `WM_QUERYENDSESSION`. Task 1.4 showed on VM 102 that the sign-out completes in about 7 seconds and that Windows itself ends the probe before `WTS_SESSION_LOGOFF` reaches the service. The end wait of D2 makes this end a session-end end. A probe that the service restarts in the ending session before the notification ends too (spike 1.4), and the service starts none after it.
- [A legitimate desktop or window gives blind samples, and D6a locks the child] → Task 1.5 checks UAC, Ctrl+Alt+Del, the secure screen saver, a fast user switch, Sysinternals Desktops, console windows, a hung program, Windows Terminal, and the largest number of foreign children in normal use (`{ "blind": "children" }`). Task 1.5 ran them on VM 102 without a blind sample; a fast user switch and Windows Terminal did not run. The strike after the first lock makes a false blind sample costly, so task 9.1 repeats the open checks on the child's PC before the release (D15), and the shadow mode (D12) then checks the child's PC for some days before any probe lock applies.
- [The console window and the tid→pid test (S18)] → For a console window, `conhost.exe` reports a client process as the owner (`ConsoleSetWindowOwner`). The docs do not say whether the reported thread belongs to that process. If it does not, the test of D3b gives Ended for each console window in front, which fills the budget in a few samples. Tasks 1.2 and 1.5 check it with cmd, PowerShell, a console whose first client ended while another client stays, and Windows Terminal. The named fallback is: the probe adds the flag `fgConsole: true` to a sample if the class of `fg` is `ConsoleWindowClass` (the service in session 0 cannot read the class of a window of another session), and the service then reads that `fg` process by `pid` alone and skips the thread test. A game that registers this class only makes its own process the `fg` entry, so this gives no bypass.
- [A clock step] → The outcome of an entry does not depend on the wall clock after S14 (D3b). The start-time test of the WebView2 parent chain does, so its failure counts nothing and is not blind (D5).
- [Sleep and resume (S20)] → A resume restarts the watchdog and the outage timer, the first sample after it adds zero, and an end of the probe within 15 seconds after it is a benign end (D2). The timers use the unbiased interrupt time, so a late power event does no harm. Task 1.6 measures it; task 1.7 records Modern Standby.
- [A click on the widget of the agent (B6)] → The widget is non-activating (D5). Task 1.2 proved it on VM 102 with a spike widget: no click and no `DragMove` changed the Foreground Window, so the move is `DragMove`, and the fallback is not needed. Task 6.2 checks the real widget.
- [Windows 11 (S18)] → The VM is Windows 10 22H2, and the README supports Windows 11. On Windows 11, Notepad is a Store app (Unknown, not System), and the taskbar, Widgets (a WebView2 host from the Store) and Start differ. Task 9.1 records the OS of the child's PC; if it is Windows 11, the checks of tasks 1.2 and 1.5 run on Windows 11 too before the release (D15).
- [A CPU load stalls the probe (spike 1.5)] → On VM 102 the gaps reached 34.2 seconds; the cause is not confirmed (D2). The gap rule of D5 counts a gap with the same programs at both ends, at most 60 seconds, and makes each other long gap a budget item. A sample that itself takes more than 12 seconds counts at most 12 seconds and is a budget item. Each gap over 12 seconds writes `PROBE_GAP`, and the parent gets one alert per day. The child controls both ends of the stall: it starts and stops its own load (for example High priority of its game in Task Manager, without a script). So it can show the same Study window at the start and at the end of a stall and play a game in the middle; the gap then counts in Study, at most 60 seconds per gap. This is accepted as class 6 of the list of D13, and the alert shows it to the parent. Task 9.1 repeats the load on the child's PC.
- [A hung program counts as its program (spikes 1.2 and 1.5)] → The ghost rule of D4 counts a hung game as the game. A Study program that hangs in front counts in Study for as long as it hangs. A ghost window that the probe cannot resolve keeps the category of the last sample while that process runs.
- [A suspended WebView2 app] → The service suspends the creator of a WebView2 control when its category is exhausted, but never `msedgewebview2.exe` (`ProtectedPrograms`). If the control still takes input and draws while its host is suspended, a web game in it plays on, and nothing counts, because the creator is suspended. The docs do not say what happens. Task 1.2 checks it. The named fallback is: a trusted WebView2 entry whose creator is suspended counts under the rule of a program that is never suspended (D5).
- [The rule of D5 counts a legitimate program in a second category] → `children` and `cursor` with `WS_EX_NOACTIVATE` add entries that normal use rarely has (B3), but a program that hosts a window of another process (an OLE server, a plug-in host, a launcher) would also charge that process. Task 1.2 logs `fg`, `focus`, `children` and `cursor` for common programs (Office, a browser, a WebView2 app, a Store app, a game launcher) and for one hour of normal use, with the largest number of foreign children per program. Task 9.1 runs this on the child's PC before the release (D15). If a common case gives a wrong category, run `/opsx:update` before the release. The named fallback for `cursor` is a suspend candidate only, without time.
- [An untrusted WebView2 locks a Study app user] → A Fixed Version or per-user `msedgewebview2.exe` counts by its own App Rule, and the file name is never suspended, so an exhausted Unknown can lock (D5, B4 trade-off). Task 1.2 lists each WebView2 path; the parent can add an App Rule; GitHub issue #48 moves the protection to the path test.
- [A suspended exe is not counted, but a sampled exe is a suspend candidate] → A `cursor` exe without `WS_EX_NOACTIVATE` becomes a suspend candidate, so a background program that the cursor passed over is suspended when its category is exhausted. This only suspends, as the hard rule allows, and the child gets it back with time of that category.
- [After a service restart `ForegroundHistory`, the blind budget and the strike are empty] → Unchanged trade-off of `add-app-categories` D3b for the history. With about 5-second samples the set fills fast. Only an administrator can restart the service.
- [The stage 2 changes `usage-breaks` (#31) and `blocked-programs` (#33) are merged and archived] → Continuous Use does not read agent data, and its scenario "Agent samples do not count" stays true (the route answers 404). The Blocked Start reads the exe from the process; it gets the benefit of `SeDebugPrivilege` (D3b).

## Migration Plan

1. Task 1.0 (a chore PR before group 3) moves all projects to .NET 10, CI and the snapshot `test-base`.
2. Before the release tag, the release gates of D15 (task 9.1) run on the child's PC with a log-only spike build.
3. One release contains the probe, the channel, the new agent and the installer change. The probe locks are off (D12). The change of GitHub issue #48 is applied and archived after this change and before the release tag (S22, task 7.4).
4. The installer stops the service and the agent, removes the `Run` value, installs `{app}\probe`, and starts the service.
5. The service starts a probe and an agent in each existing session of a Restricted User, and an agent in each other session.
6. After task 9.1 passed and at least 7 days of shadow mode on the child's PC without a false "would lock", the parent switches the probe locks on in the web admin (D12, D15).
7. Rollback: an install of the previous version brings back the HTTP routes, the `Run` value and the old agent. No table and no column change, so the database needs no rollback.

## Open Questions

None that change the specs or the tasks. The VM spike (group 1) measured the constants on VM 102, and task 9.1 measures the rest on the child's PC: the sample interval (0.2 s + exponential with a mean of 4.8 s, at most 10 s), the bound of 8 foreign child processes, the bounds of the cursor chain (8 processes, 32 steps), the gap rule (12 s, and 60 s with the same counted processes), the blind budget (6 in 10 minutes), the watchdog (30 s), the end wait after the end of a probe (90 s), the restart delays (1, 2, 5 s), the count of unexpected ends (3 in 10 minutes), the resume window (15 s), the long sample (12 s), the timeout of the cursor call (1 s, only in the fallback of N28), and the agent allowance (60 s in 10 minutes).
